# Dogfood: The 2026-11-02 Round — a "//" was a comment in every language

## 11. The 2026-11-02 Round

### 11.1 The symptom

Two commits, in two languages, and the tool said the same thing about both:

> This change did not alter the behavior of the code — it needs no new test
> … but the changes are only comments and whitespace outside the string
> literals.

The first was a Python commit:

```python
 def total(count, batch):
-    return count // batch
+    return count // batch - 1
```

The second was a Go commit:

```go
-//go:build linux || darwin
+//go:build linux || darwin || freebsd
```

Both are real changes. The first changes the value of every batch. The
second moves the file between platforms — a build constraint decides which
platforms compile it.

In both cases the test in the tree watched the change. In the Python case
the test was red before the fix and green after it. The tool did not run the
experiment, so it never saw that.

The cost is not a wrong number. It is the tool's own subject matter: the
commit the tool was built to judge was thrown away before it was judged.

### 11.2 The root cause

One rule, applied to every language:

```go
if c == '/' && i+1 < len(content) && content[i+1] == '/' {
    i = skipToLineEnd(content, i)
    continue
}
```

A `//` opens a comment. In Python it opens floor division. In Go it opens a
comment — except when it opens `//go:build`, which is a build constraint and
not a comment at all.

The rule was in the engine, and the engine held no grammar. So it could not
tell those apart, and it applied the same answer to everything.

The evidence line the report printed said so:

> a // comment is removed wherever it starts

That sentence was false for every language it was applied to. In Python
there is no `//` comment to remove. In Go a `//go:build` is not a comment.
And it was printed as the evidence for the conclusion, so a reader checking
the tool's work would have found the difference.

The rule's own comment said which way it should have erred:

> Getting this wrong in the "hide a real change" direction would lose a
> finding. So every rule here errs towards keeping the text.

It did not err that way. It hid real changes.

### 11.3 The fix: the question moved to the layer that knows the language

The engine no longer reduces anything on its own. It asks the adapter:

> can you CONFIRM this change touched nothing but formatting and ordinary
> comments?

That is a new optional capability, `core.CosmeticConfirmer`, and it is the
shape the other optional capabilities already have (`IsTestPath`,
`IsSourcePath`, `CompileChecker`, `TestDiscoveryAuthority`,
`WorktreePreparer`). The engine asks; the adapter answers.

The verb is the point, and it is a different question from the one the
engine used to ask itself:

| | the question | what it costs to answer it |
|---|---|---|
| the old rule | "where are this language's comments?" | a rule per language, and a hole for every language it does not cover |
| the new one | "can you confirm this change is cosmetic?" | one answer per change, and "no" is always available |

An adapter that cannot be sure says no, and the engine runs the experiment
as it always does. The two mistakes cost different amounts: a "yes" that
turns out to be a behaviour change skips the experiment and loses the
finding; a "no" that turns out to be a comment-only change costs one test
run and says nothing false.

So the rules the adapters hold are small, and they are facts about a
language rather than a list to maintain:

- Go: `//` and `/* */` are comments; `//go:`, `// +build`, `//export` and
  `//line` are directives and are **kept**.
- Python: `#` is a comment; `//` is **not** a comment and stays in the text.
- JavaScript/TypeScript: `//` and `/* */` are comments.

The reduction that does the work — literals kept whole, whitespace outside
them removed, an unclosed quote or block comment meaning "I could not read
this" — is one implementation, shared, because a rule that exists in three
places is three rules that will drift. It lives in `internal/adapters`
next to `IsTestFilePath`, which is shared for the same reason.

### 11.4 The three answers, and why "cannot tell" is one of them

The capability has three answers, not two:

| answer | what the engine does |
|---|---|
| confirmed cosmetic | skips the experiment; the commit is "not applicable" |
| confirmed a real change | runs the experiment; the ordinary verdicts apply |
| **could not tell** | **runs the experiment, and a green suite accuses nothing** |

The third one is the reason the answer is three-valued. "Could not tell" is
not "no": some syntax the change touched is outside what the adapter's rules
cover, so the change might have been nothing but formatting.

And a green suite says nothing about a change whose nature is unknown. So
the verdict there is a new one — `uncertain` — and it is not a gap and not a
pass. It is an admission:

> Cannot be judged: this change may be nothing but formatting, so a green
> suite does not accuse the tests of anything

Without it, the engine would have had to choose between two bad answers:
accuse a reformat of accusing a commit that did nothing, or skip the
change and lose a real one. The engine's own rule says the second is the
worse mistake ("missing a real finding is far worse than reporting a
cosmetic one"), but a third answer is better than either.

An adapter that does not implement the capability at all can only answer
"could not tell" — so every change in a language without the capability
reaches the experiment, and a green suite there is an admission rather than
an accusation. That is slower and noisier, and it is the safe direction.

### 11.5 The evidence line is now a fact

The report's evidence used to be a fixed sentence describing a rule the
engine no longer has. It is now what the adapter actually did:

> Go: the `//` and `/* */` comments were removed from outside the string
> literals, and the `//go:` build directives were kept - a build constraint
> decides which platforms compile the file, so it is not a comment

> Python: the `#` comments were removed from outside the string literals, and
> `//` was kept - `//` is floor division in Python, not a comment, so a change
> to it is a change; the indentation was compared as well, because in Python
> the indentation is the block structure

An evidence line is the one thing in the report a reader checks. It has to
be true, and it has to be about the check that was performed.

### 11.6 Reproduction

The two cases, as they were run:


After:

```

Proven by these tests:
  459d0d7 — python3 -m pytest -v --tb=short -p no:cacheprovider …
    test_calc.py::test_total — green with the fix, red without it
Summary: proven 1 · vacuous 0 · no test 0 · undecidable 0 · not applicable 0
```

```
# Go
$ vacuous --mode audit --commit HEAD
```

Before:

```
  [    INFO] no-test-for-fix      platform.go
      This change did not alter the behavior of the code — it needs no new test
Summary: proven 0 · vacuous 0 · no test 0 · undecidable 0 · not applicable 1
```

After:

```
  [    WARN] no-test-for-fix      platform.go
      This change altered behavior and nothing in the repository is watching it
      Detail: Commit f7395db changed 1 non-test files (the largest of them
      changed 2 lines) and added no test at all.
      With this fix removed, every test **already in** the repository passed
      (1 passed, 0 failed, 0 skipped)
```

The Go verdict is a finding, and it is the right one: the commit changed
which platforms the file builds on, and no test in the repository watches
that. The tool cannot see freebsd from the machine it runs on — and it no
longer pretends the change was nothing.

### 11.8 What this round does not cover

★ **The language rules are still not a grammar.** They say what a comment
is in three languages, and — after §12 — what the layout means in them. They
do not parse the language, so they do not see a layout rule finer than
"where does a statement end" and "how far is this line indented":

- a heredoc's body is its output, and the tool has no heredoc language;
- JavaScript's own semicolon insertion is wider than the rule that reads it.
  The rule asks "could a statement end here?", and it answers yes after an
  identifier, a literal, a closing bracket and `++`/`--`. JavaScript inserts
  a semicolon wherever the next token could not continue the expression, so
  a change shaped like `a\n+b` is read as a moved statement when
  JavaScript would have continued the expression. That is the loud
  direction, and the tool says "I cannot tell" rather than claiming either
  way.

★ **The size of a change is now measured from the whole file**, not from
the changed lines. A line read on its own cannot know whether it sits
inside a literal that opened earlier, so the file-level reading is the
authoritative one. That is a change in the numbers the report quotes: they
are the same measurement the verdict uses, and they are occasionally
different from what the old diff-level count said.

★ **An adapter for a new language now has a second thing to implement.**
`core.CosmeticConfirmer` is optional, and an adapter that does not
implement it will run the experiment for every change. The cost is a test
run per commit; the benefit is that the engine never grows a rule about a
language it does not know.

## 12. The 2026-11-02 Review Round — the rule that had no test

### 12.1 Why there was a review

The change in §11 is the one this project is most likely to get wrong: it
changes what the tool is allowed to **claim**. A rule that says "this change
did not alter the behaviour" is a sentence with no way out for the reader who
believes it, and the rules that produce it had been wrong twice already.

So the change went to an independent review — an agent that had not written
the code and was given the diff, the project rules, and the job of finding
what was wrong with it. It could build both versions and run both.

It returned **PARTIAL**, with eight findings. Every one of them was
reproduced independently before anything was changed, and every one of them
was true.

### 12.2 The expensive one: the third answer had no test

★ **The rule I had just written — "could not tell" — was not covered by a
single test.**

The review took the branch out:

```go
if run.cosmeticUncertain {
    return VerdictUncertain
}
```

deleted the finding that goes with it, and ran the whole suite. **The suite
stayed green.**

That is the failure mode this project exists to avoid, and it was sitting in
the change that was supposed to fix it. The three-valued contract existed on
paper: `core.KindUncertain` was a constant, `VerdictUncertain` was a
verdict, the report had a sentence for it — and nothing held any of it down.

It is fixed now, and the fix is the shape the project already uses — the
control that goes red when the rule is taken out:

| control | what it pins |
|---|---|
| `TestAGreenSuiteIsAnAccusationOnlyWhenTheChangeWasClassified` | the rule itself: an unclassified change with a green suite is `uncertain` and not `vacuous` |
| `TestAGreenSuiteDoesNotAccuseAChangeNobodyCouldClassify` | end to end, on a real Python repository: no accusation is filed |
| `TestTheUncertainVerdictFilesItsOwnFinding` | the verdict is reported, not swallowed |
| `TestARedSuiteOutranksTheUncertainty` | a red suite settles the question the adapter could not |

### 12.3 The regression: a deleted file's size came out as zero

The change moved the size of a change from the diff's own reading to the
adapter's. The adapter cannot measure a file whose language it does not
speak, so it falls back to the diff's count — and the diff's count was keyed
on the **`+++` side** of the diff.

A deleted file's `+++` header is `/dev/null`. So every deleted file's lines
were filed under a path that does not exist, and the file's own count came
out as zero.

The report then said:

> the largest of them changed 0 lines

next to a change that deleted twenty lines — and the severity of a real
finding fell from **high** to **warn**, which blocks nothing. A CI gate
that used to fail stopped failing.

The fix reads the path from the `---` side when the `+++` side is
`/dev/null`, and the control is
`TestRawLinesPerFileNamesTheFileTheDiffDeleted`.

★ **The same reader had a second defect, and it was older.** It took any
line starting with `---` for a file header. A line of a SQL file that
begins with `-- ` comes out of a diff as `--- ` — which is what a file
header looks like. The count of a twenty-line file came out as zero. That
one is dogfood bug **3.112**, and the fix is to read the diff the way it is
written: the headers come before the first hunk, and everything after `@@`
is content.

### 12.4 The contract was still overclaiming

The capability is named `CosmeticConfirmer`, and the question it answers is
"can you **confirm** this change touched nothing but formatting?" — and the
adapter confirmed two things it cannot confirm:

- **Python's indentation.** The reader threw away every piece of whitespace,
  so a statement moved four spaces to the right reduced to the same text and
  was called a reformatting. In Python the indentation *is* the block
  structure, and the statement had moved into another block.
- **A statement that ends in a different place.** `return x` and
  `return\nx` are different programs in Go and in JavaScript — both insert a
  semicolon where the line ends — and the reader called them the same.

★ **Both were the same defect as the one §11 fixed, one layer out:** a
whitespace-blind rule, written for a language whose whitespace is not
layout. The fix is the same shape as the fix in §11 — the reader asks the
language, and the language says what its layout means:

```go
type LayoutRules struct {
    IndentationIsSyntax     bool // a line's indentation says which block it belongs to
    LineBreakEndsStatement  bool // a break at the top level of a statement ends it
}
```

Python says yes to the first, Go and JavaScript say yes to the second, and a
change that moves either of them **cannot be confirmed** to be formatting —
so the adapter answers with the third value, and the verdict is `uncertain`.
Dogfood bug **3.111**.

★ **The rules that read the layout are the ones that say what a statement
ends after** — an identifier, a literal, a closing bracket, `++`/`--`. A
line that ends in an operator continues onto the next one, and its break is
layout. Without that distinction every reflow of a long condition would be
"I cannot tell", and a rule that cannot tell is a rule nobody reads.

### 12.5 The smaller ones

| finding | what it was | what it is now |
|---|---|---|
| The suppression table did not know `uncertain` | `// vacuous:ignore uncertain` silenced **every** kind, because the word was not in the table | `uncertain`, `contradictory` and `audit-failed` are in the table |
| The architecture's verdict table had no `uncertain` row | the vocabulary was incomplete in the document that defines it | the row is there |
| The evidence sentence lost a limit | "the `//` comments were removed" is false for a file that holds a URL | "removed from outside the string literals" |
| Two behaviours lost their test when the engine's reader went away | a literal that spans lines, and a stray quote that must not swallow the file | both moved to the adapter, where the reader lives now |
| The consistency check did not look at the uncertain verdict | a runner output that says "FAIL" could sit next to an uncertain verdict | the uncertain verdict is checked like the vacuous one |

### 12.6 The claim in the pull request that was not true

The pull request said the change was verified over thirty commits:

```
vacuous --mode audit --limit 30
```

★ **That command covers one commit.** `--limit` says how many commits to
judge, and the base is the merge-base of `main` and `HEAD` — which, on a
branch with one commit on top of `main`, is `main` itself. So the run judged
one commit and the description claimed thirty.

The command that does what the description said is:

```
vacuous --mode audit --base HEAD~30 --limit 30
```

and it gives the same answer on both versions of the tool
(`undecidable 1 · coupled 1`), so the claim was true and the sentence that
made it was wrong. The sentence is the bug: a verification claim that
describes a command which does not do it is worse than no claim, because a
reader who runs the command gets a smaller answer than the one promised and
has no way to tell which of the two is wrong.

★ **This is the same shape as the rest of this round.** The tool's own
subject is a claim about what a test watches. A claim about what a command
checked is the same kind of claim, and it has to be true in the same way.
