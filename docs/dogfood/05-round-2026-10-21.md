### Verifying one "proven" verdict by hand — pre-existing red lights are correctly excluded

**Why verify by hand**: every verdict the tool produces is "the result of running something", but the reader cannot look at those two trees for themselves. One end-to-end manual reproduction is the only way to prove "the guard it recognized is real". (Originally numbered 3.42; the number was removed because it collided with an earlier entry.)

**Scenario**: a commit in a Python repo (using unittest). The tool judges it **proven**.

**Manual reproduction** (following the tool's own recipe):

```
# the counterfactual tree = the parent commit + only the test patch (the fix stays out)
git archive <commit>^ | tar -x -C /tmp/verify
git diff <commit>^ <commit> -- 'scripts/test_build_docs_site.py' | git apply
cd /tmp/verify && python3 -m unittest discover -v -s scripts -t scripts -p 'test_*.py'
```

**Result**:

| | Counterfactual tree (fix left out) | Baseline tree (this commit's own tree, with the fix) |
|---|---|---|
| Failing cases | 5 | 2 |
| The test newly added by that commit | **red** (1 error + 2 parameterized fails) | **green** |
| Missing submodule `access/docs` of the API relay | Red | Red |
| Another module's Python 3.9 f-string syntax | Red | Red |

**The set difference is exactly the 3 cases of the test file newly added by that commit** — all of them red because the fix was reverted. The two **pre-existing** red lights (the missing submodule, the Python version syntax) are red on both sides, **correctly excluded**.

**This is exactly what "compare sets, not counts" is for**: this repo's suite already had 2 red lights; an implementation that only compares counts would fold them into "the ones that turned red because the fix was reverted". This implementation does not.

It also shows one thing: **the "proven" verdict itself can be independently re-checked by a third party** — the tool writes the recipe into the report, and a reader who follows it can see where each of the two trees is red. If the recipe is wrong, the conclusion is void.

**Negative control**: all 8 break points were measured with "break it → red → put it back", **0 false negative controls**. 4 of them are end-to-end / cross-layer (`Go.IsTestPath`, `audit.isSource`, `detect.isTestPath`, `discarded.go`), 4 are single-layer.

**A note that pointed the wrong way, corrected along the way**: the "note" at the end of 3.45 points at `internal/git/istest.go` and says that changing it changes the verdict. **That is dead code** — `core.FileChange.IsTest` was never read outside the package; the real source of the verdict is `audit.go` → the adapter's `IsTestPath` / `IsSourcePath`. Follow the original pointer and change it, and **the verdict does not change**.

**This round's two methodologies**:

1. **The root cause of "the same judgment written in several places" has to be consolidated by "who reads it", not by "who wrote it".** This round consolidated the testdata rule into one place (`adapters.IsTestDataPath`) not because "it was written three times and that looked ugly", but because **the copy that matters for the verdict was never written at all**, while the first two copies (static check, suite discovery) had each been fixed and each thought itself finished. **The most dangerous thing about a judgment scattered across several layers is not that they disagree, it is that "no layer knows it is responsible"** — 3.45 / 3.50 were each fixed inside their own layer, so everyone thought the matter was closed. **The one the independent re-review added (`discards-error`) is exactly a second instance of that root cause**: it belongs to the "should have asked, but did not" class.
2. **The criterion has to be split by the runner's actual behavior, not by the intuition of a directory name.** This round nearly excluded testdata from the "is it a test" question for Python / Node as well — that would turn a **true positive** into a **false accusation** (pytest really does run `testdata/test_fixture.py`; measured: `pytest --collect-only` listed its two cases). **"testdata is data" holds in three languages; "testdata is not a test" holds only in Go's verdict layer**, because only Go's toolchain gives that guarantee. **The same directory name is not the same thing in different runners** — for places like this you have to look at the toolchain, not at the convention.
3. **You cannot see that your own negative control is fake.** The independent reviewer found 10 break points on their own (3 of which I did not list), broke each one → red → restored, and finally reported back one HIGH false accusation I had not seen at all (`discards-error`). **"I ran the destructive experiment myself" does not mean "the destructive experiment covered every entry point"** — a gap in coverage can only be filled by someone who does not know my conclusion.
