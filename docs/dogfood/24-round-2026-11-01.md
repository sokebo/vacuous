# Dogfood: The 2026-11-01 Acceptance Round

## 10. The 2026-11-01 Acceptance Round

An acceptance round, not a bug hunt: the question was whether the tool can
judge a **real** TDD-shaped change in a **real** repository, and the answer
turned out to be "yes, but only after the repository's own suite was made
green — and one of the answers the tool gave along the way was wrong, and
wrong in a way that belongs in this directory."

**Tool under test**: `v0.1.7-0.20261101095546-7f5703c09f95`, built from
`main` at `7f5703c` (PR #18, merged).

**Repository under test**: `example/admin-service` — a Go admin module of
the same shape as the repositories in chapter 5, whose `go.mod` points at a
sibling checkout through `replace`, read-only. Every mutation was done in a
scratch clone; the original checkout was never written to.

**Case**: upstream commit `35d9cbfb` —
`fix(importers): avoid duplicate warnings for split provider rows`
(2026-06-24, parent `3e896cef`). It changed
`internal/importers/csv_generic.go` (+26/−3) and brought two
tests with it in `csv_generic_test.go` (+55).

### 10.1 What the change does

A provider CSV can contain several rows that belong to the same
`(provider, model, period)` bucket. The old row key was built from the bucket
alone, so the second row of a bucket collided with the first and was dropped
whole, with a `duplicate_row` warning. The fix puts the row's own content into
the key.

The hand check, on the split commit, is unambiguous. With the fix removed,
both new tests are red:

```
duplicate row key "acme-main|vendor/model-x|2026-04-01|amount"
duplicate message = "duplicate provider row"
```

### 10.2 The TDD shape: the test landed in the previous commit

The upstream commit carries its tests with it. The flow this round was
meant to measure is the other one — **the author writes the test first, the
implementation lands in the next commit**. So the upstream commit was split
into two, in a scratch clone, with the **audited subtree** byte-identical to
upstream (`git diff 35d9cbfb HEAD -- internal/importers/` is
empty; the only other difference in the tree is the `replace` line in
`go.mod`):

```
c7930678 test(importers): 拆分的行不该被判成重复 —— 规格先落一笔
92e0adc8 fix(importers): avoid duplicate warnings for split provider rows
```

That split is what makes the tool's **unit of judgement** visible. The
implementation commit does not ship a test, so the tool cannot narrow its
scope to the package the change touches — it has to ask the whole module
whether *anything* in the tree watches this behaviour. Everything below
depends on that distinction.

### 10.3 The environment was broken, and it was not the toolchain

The first runs could not produce a verdict at all, and the reason is worth
recording because the obvious explanation is the wrong one.

**It was not the Go toolchain.** `go.mod` asks for `go 1.25.11`; the machine
has `go1.26.5`, and the toolchain cache holds `go1.25.11` as well. An earlier
reading of this — "the required toolchain is not available" — came from a
`GOPROXY=off` lookup failing, and mistook the failed lookup for a missing
version.

**It was not the network.** `https://goproxy.cn` answers `200`. Only
`proxy.golang.org` times out.

**It was a missing sibling checkout.** `go.mod` pins a release tag:

```

github.com/example/shared-lib v1.13.0
```

### 10.4 The suite was red for three unrelated reasons, and none of them was about the tool

With the module compiling, the whole suite could be run at all:

```
23 packages · 317 failing tests
```

| Cause | Failing tests | Where |
|---|---|---|
| `go-sqlite3` is a stub under `CGO_ENABLED=0` (no C compiler on the machine) | **308** | billing, controller, middleware, platform, service, store, router |
| `file://` URI built wrongly on Windows | **8** | artifact (6), importers (1), workflow (1) |
| `filepath.IsAbs` does not treat `/abs/x` as absolute on Windows | **1** | artifact (1) |

The first row is a fact about **this machine** (no C compiler, so
`CGO_ENABLED=0` and `go-sqlite3` is a stub). The second and third rows are
**real bugs in the audited repository**, and they are invisible on POSIX: a
POSIX path already starts with `/`, so the URI comes out identical to the old
one and every test stays green. Whether the repository's own CI would have
caught them is not something the repository answers — its `ci.yml` runs on
`group: <default>`, a self-hosted runner group whose operating system the
repository does not declare (only `prod.yml` pins `ubuntu-latest`).

**The URI bug.** The writer built its URI like this:

```go
uri := (&url.URL{Scheme: "file", Path: targetPath}).String()
```

On Windows `targetPath` is `C:\Users\...`, and `url.URL.String()` produces
`file://C:%5CUsers%5C...` — the drive letter becomes the *host*, and the
next `url.Parse` fails with `invalid port ":%5CUsers%5C..."`. Measured
directly:

```
A raw String():       file://C:%5CUsers%5CAdministrator\AppData\Local\Temp\x.json
B ToSlash+/prefix:    file:///C:/Users/Administrator/AppData/Local/Temp/x.json
C parse B err=<nil> host="" path="/C:/Users/Administrator/AppData/Local/Temp/x.json"
D Abs(u.Path)="C:\C:\Users\Administrator\AppData\Local\Temp\x.json" err=<nil>
E linux String():     file:///tmp/x.json
```

Line **D** is the second half of the bug: even with a correct URI,
`filepath.Abs("/C:/Users/...")` yields `C:\C:\Users\...` on Windows, and
`os.ReadFile("/C:/Users/...")` fails outright:

```
ReadFile("C:\Users\ADMINI~1\AppData\Local\Temp\uritest-probe.txt") -> "hello" err=<nil>
ReadFile("/C:/Users/ADMINI~1/AppData/Local/Temp/uritest-probe.txt") -> "" err=open ...: The filename, directory name, or volume label syntax is incorrect.
```

Line **E** is what makes the bug survivable upstream: on POSIX the path
already starts with `/`, the URI comes out identical to the old one, and
every test stays green. The upstream `develop` branch still carries the same
`(&url.URL{Scheme: "file", Path: path}).String()` in its test helpers — the
bug is real, and nothing in the repository's own workflows exercises it on
Windows.

**The path guard.** `resolveWritablePath` rejects absolute paths with
`filepath.IsAbs(rel)`, but on Windows `filepath.IsAbs("/abs/outside.json")` is
**false**, so the guard let a rooted path through.

The fix, applied only in the scratch clone (the original repository was not
written to):

- `artifact.FileURIFromPath(localPath)` — `ToSlash` plus a leading `/`, so
  Windows produces `file:///C:/...` and POSIX output is unchanged.
- `artifact.LocalPathFromFileURI(u *url.URL)` — strips the leading `/` before
  a drive letter and converts the separators back, so `os.ReadFile` gets a
  path the OS accepts.
- the reader hands the **local path** to `storage.ReadAll` rather than the
  URI, because the sibling's file backend passes `url.Path` straight to
  `os.ReadFile`.
- the relative-path guard also rejects a rooted path by separator prefix,
  which `filepath.IsAbs` misses on Windows.

**The third red light was not a platform bug at all.** One test asserted
`len(resp.Data.Checks) != 3` while the readiness service returns four
checks — the `platform_extract_config` check had been added without the
assertion following it. Upstream fixed exactly this in `7e5d0ff1`
(`-if resp.Data.OverallStatus != "ok" || len(resp.Data.Checks) != 3`
`+if resp.Data.OverallStatus != "ok" || len(resp.Data.Checks) != 4`). The
scratch clone took the same change.

With all three addressed, and with a C compiler installed by hand from the
WinLibs release archive (`BrechtSanders.WinLibs.POSIX.UCRT` 16.2.0 — winget's
download step failed, so the archive was fetched with `curl` and unpacked to
`C:\tools\winlibs`), `CGO_ENABLED=1`:

```
FAIL packages: 0
ok packages: 23
```

**The whole module's suite is green on Windows after this round** — that is
what this round measured, and it is the first time it was measured here.

### 10.6 A bug in the tool: the consistency check reads the test names

Row 8 is the wrong answer, and it is worth being precise about what the truth
was.

The truth: `vacuous`. The spec was neutered so that removing the fix leaves
every test green, the whole suite is green on both sides, and the tool's own
evidence says so:

```
command: go test -json -count=1 ./...
result: 792 passed · 0 failed · 0 skipped
```

792 passes, 0 failures, 0 skips — reproduced on three consecutive runs of that
checkout (two of the streams were kept), with 0 `"Action":"fail"` events each
time.

The two trees are **not** the same tree, and the difference is the whole point
of the case. The audited commit changed exactly one file
(`internal/importers/csv_generic.go`), so:

- the **counterfactual** tree — the commit with the fix taken out — is the
  parent's tree exactly;
- the **baseline** tree — the same commit with the fix in place — is that
  tree plus the one production file.

`git diff --stat 130e394f 0e75adf1` is one file, 26 insertions and 3
deletions. The two runs are therefore two different trees, and **because the
spec was neutered, no test observes the difference**: both sides report 792
passed · 0 failed · 0 skipped. The change is real, the tree differs, and
nothing watches it. That is what `vacuous` means — and the tool refused to
say it, because it compares the verdict against a substring scan of the
output rather than against the parsed event stream it already has.

What the tool said:

```
contradictory :: The tool's conclusion and its own raw output disagree — this is a bug in the tool, not in your code
  Detail: The judgement of commit 0e75adf1 contradicted itself: the verdict says every test passed,
  but the runner's own output contains a failure — the parse is probably wrong.
```

`contradictory` is `critical`, and it means "the tool is broken, please
report it". The tool was not broken. **The check that fired was reading the
test names and the tests' own output.**

The consistency check compares the verdict against the runner's own output,
and it decides "the output contains a failure" with a substring scan over the
**whole stdout**:

```go
var failureMarkers = []string{
	"FAIL",
	"build failed",
	"panic:",
}
```

But the stdout of `go test -json` is not a test report — it is a **JSON event
stream that embeds the test names and the tests' own output**. Nine lines in
the audited repository's stream carry a marker — eight contain `FAIL`, one
contains `panic:` — and they belong to **three test names, every one of
which passed**:

```
{"Action":"run","Package":".../internal/store","Test":"TestStoreRerunArchivesOldAndCreatesNew/FAILED"}
{"Action":"pass","Package":".../internal/store","Test":"TestStoreRerunArchivesOldAndCreatesNew/FAILED","Elapsed":0}
{"Action":"output","Package":".../internal/middleware","Test":"TestAuditLog_RecordsPanics","Output":"\tgopanic: fn()\n"}
```

(These three lines are excerpts: the `Time` field is dropped and the package
path is shortened. The self-test line quoted further down is verbatim.)

The first is a **subtest whose name is a status name** — table-driven tests
name their cases after the state they exercise, so `.../FAILED` is a passing
subtest — and there are two of them, one in `internal/store` and one in
`internal/service`. The third is a test that **panics on purpose** to
prove the recovery middleware catches it; the middleware catches it, the test
passes, and its stack trace still contains `panic:`.

A repository where **passing subtests are named after failure states** is not
unusual — it is the ordinary way to write a table-driven test over states.
Such a repository gets `contradictory`, `critical`, and a report that says the
tool is broken, when the actual finding is "this change has no test watching
it".

**And this repository is such a repository.** Running the tool's own suite
produces a **passing** subtest whose name carries the marker:

```
{"Time":"2026-11-01T20:38:13.3048457+08:00","Action":"pass","Package":"github.com/sokebo/vacuous/internal/counterfactual","Test":"TestCheckConsistencyCatchesAContradiction/the_verdict_says_everything_passed,_but_the_output_says_FAIL","Elapsed":0}
```

That is the consistency check's own test case, and its name contains "FAIL".
So on this repository, at whole-module scope, the tool's own test names turn
every `vacuous` verdict into `contradictory`. **The condition is not exotic —
it ships with the tool.**

**Why it only shows up at whole-module scope.** The scan is over the whole
stdout of the run, and the run's scope decides which packages contribute
their output to it. The `importers` package alone (rows 9–11) contains
neither of the two `/FAILED` subtests nor the panic test, so the same scan
comes back clean and row 11 is `vacuous`. The full module contains all three,
and row 8 is `contradictory`. **The false positive is a function of the
scope**, which means it will hit a different repository, a different commit,
and a different answer each time.

**Where the fix belongs.** For Go's `-json` output the failure is already in
the event stream — `"Action":"fail"` — and the adapter parses that stream
already (`parseGoEvents`). The raw substring scan is the right idea for a
runner whose only output is text, and the wrong idea for one whose output is
structured: the structured answer should be preferred when it is available,
and the substring scan should not be allowed to overrule it.

**Not fixed in this round.** The finding is recorded here; the fix is a
separate change, and this round does not touch the tool's code.

### 10.7 What the tool can and cannot say about a weakened spec

Rows 6 and 7 differ by one deleted assertion, and the tool's output for them
is **identical** — same verdict, same two witnesses, same test names.

The honest reading is narrower than "the tool cannot see that the spec
changed":

- The weakened variant deleted the assertion that no two rows share a row
  key. The test **still** catches the regression, through a coarser
  assertion (`RowsParsed != 2 || len(result.Rows) != 10`). So `proven` was
  the **right** verdict for the weakened spec, and the identical output is
  not wrong.
- What the tool cannot say is **which** assertion was doing the guarding. It
  certifies "there is a test whose behaviour flips with this change", not
  "this assertion is the one that guards it".

That distinction matters for the workflow this tool is meant to support. In
"the author writes the test, the implementation lands later" the test file is
inside the editor's reach, so a weakened test and an unmodified test produce
the same report. **The freeze on the test side has to come from git** — the
diff of the test side, compared against the spec commit, is what says whether
the guard was moved. The tool cannot substitute for it, and this round
measured exactly where it stops.

### 10.9 What this round does not cover

- **The original repository was never modified.** Every commit above lives in
  a scratch clone. The URI fix, the path guard and the readiness assertion
  exist only there; the upstream repository still has all three problems.
- **The `contradictory` finding is a finding, not a fix.** The tool still
  carries the substring scan, and any repository with a state-named subtest
  can still get `critical` and a "the tool is broken" report. **This
  repository included** — see 10.6.
- **Only Go was measured.** The Python adapter carries the same substring
  scan and would misfire the same way on a test that prints "FAILED"; the
  Node adapter sets neither `RawOutput` nor `RawFailed`, so on Node the
  consistency check never runs at all. Neither adapter was exercised in this
  round.
- **This repository's own suite is red on Windows** — 20 failing tests
  (adapters 15, counterfactual 3, gate 2) out of POSIX path assumptions and
  the same `file://C:%5C...` URI construction the audited repository has. The
  tool has never run its own suite on Windows; that is a separate piece of
  work.
- **One repository, one case.** The scope rules in 10.5 were measured on a
  Go module with a `replace` on a sibling checkout; a repository whose
  scope rules work differently was not tested.
