# DOGFOOD

这个文件记录 vacuous 在**真实仓库**上的运行结果，以及每一个发现是怎么被
人工核实的。

一个只会说自己准的工具没有价值。这里的每一条发现，要么有独立的复核记录，
要么就说明它是错的 —— 而后者恰恰是这份文档最有价值的部分。

- 运行环境：macOS (darwin/arm64)，Go 1.26.5
- 被审计的仓库：本地已有的 6 个仓库，没有一个是为本项目造的
- 复核方式：每一条高危发现都回到 git 原始提交、用**工具之外的手段**重新
  验证一遍

**脱敏说明**：这份文档最终会公开，而它描述的几个仓库都是私有的 —— 公开文档里
不该出现它们的内部结构。所以仓库名、内部路径、外部仓库的 commit SHA 都换成了
占位符。

| 占位符 | 它是什么 |
|---|---|
| 仓库 A | Go · 一个服务仓（反事实审计的主要靶子） |
| 仓库 B | Go · 一个库仓（带 git hooks 守卫） |
| 仓库 C | Go · 私有研究仓，7 个独立 module |
| 仓库 D | 一个公开的文档仓 |
| 仓库 E | Node · 一个前端仓 |
| 仓库 F | Node · 一个主题包仓 |
| 仓库 G | Go · 跨仓协作的 admin 仓 |
| 仓库 H | Go · 跨仓协作的 relay 仓 |
| 仓库 I | Python · 一个 harness 仓 |
| 共享库 S | 仓库 G / H 共同依赖的**同级目录**库 |
| `⟨sha⟩` | 外部仓库的某个提交 |
| `<本地路径>` | 本机上的目录 |

对照关系只存在于作者和定时校验任务的配置里。**本仓自己的 commit SHA 没有被
替换** —— 这个仓要公开，它的提交历史本来就公开。

**基线**（定时校验任务靠它判断「有没有新东西」）：

基线量的是**代码的指纹**，不是「最后一次提交是谁」。原因写在 3.18 里 ——
拿 commit 当基线的话，每一轮核验自己产生的文档提交就会把基线弄失效。

```
scripts/gate.sh check     # 退出码 0=没变 1=变了 2=判不出来
```

判据 = 四样东西：

1. **代码指纹** —— HEAD 上除 `docs/` 和 `*.md` 之外所有被跟踪文件的内容哈希
   （`internal/gate/gate.go` 里的 `Fingerprint`）。改文档不改指纹；改代码、
   改 CI 配置，指纹就变。
2. **工具自己的工作树** —— 改了没提交的东西（`DirtyPaths`，见 3.23）。指纹只量
   HEAD，核验跑的是工作树里的代码：两者不是一份，就不能报「没变化」。
3. **被审计仓库的 HEAD** —— 6 个仓，任何一个往前走一步都要重跑。
4. **被审计仓库的工作树指纹** —— 那些仓改了没提交的东西（见 3.62）。check 读的
   是工作树，不是 HEAD —— HEAD 相同不等于结果相同。

第 2 条和第 4 条的口径不一样，这是有意的：

- 工具自己的仓用「**现在是脏的就算数**」：它归我们管，工作树脏了就是「这次
  核验跑的不是 HEAD 里那份代码」，必须重跑。
- 被审仓用「**和上次记录时不一样才算数**」（记基线时把工作树指纹一并记下）：
  被审仓不是我们一个人的 —— 某个仓的工作树里一直有别人正在开发的未提交源码，
  按「脏就算数」来算，闸门会每轮都喊「有变化」，正是 3.18 那个自毁的毛病
  （见 3.62）。

机器可读的状态在 `.git/vacuous-gate.state`，**不入库**：它是这份 clone 的
状态，不是仓库的内容 —— 写在仓库里的话，每记一次状态就多一次提交，基线就
又失效一次。

**这里不抄指纹的值**：指纹天生随代码变，抄进文档就等于抄了一份注定过期的
记录（下面这份被审计仓库的 HEAD 同理）。要看当前值，跑
`scripts/gate.sh check`。

```
仓库 A  ⟨sha⟩
仓库 B  ⟨sha⟩
仓库 C  ⟨sha⟩
仓库 D  ⟨sha⟩
仓库 E  ⟨sha⟩
仓库 F  ⟨sha⟩
```

### 逐条核实

**仓库 A `app_test.go:115` — `discards-error`（高危）**
断言写的是 `len(forC) != 0`，而 `forC` 的错误被 `_` 丢掉了。加载失败时
`forC` 为空 → `len(forC) != 0` 为假 → 断言通过 → 测试报成功，实际什么都没
加载到。**真阳性。**

**仓库 A `cmd/seed/main.go:91` — `discards-error`（高危）**
```go
existing, _ := st.List()
if len(existing) > 0 {
    fmt.Printf("库里已有 %d 条。要继续追加吗？先清空用 -clear\n", len(existing))
    return
}
```
`st.List()` 的错误被丢掉。读库失败时 `existing` 是空的 → `len(existing) > 0`
不成立 → 那个「库里有数据就别继续追加」的检查**不会执行** → 程序接着往一个
自己都读不出来的库里追加数据。**真阳性。**

（注意这一条和上一条形状不同：上一条被架空的是**断言**，这一条被跳过的是
**保护性中止**。第一版工具把两者用同一句话描述，这一条因此被说成了
「断言通过」—— 结论对，解释错。见第 3.7 节。）

**仓库 B `.githooks` — `guard-not-installed`（严重）**
`.githooks/pre-push` 存在且可执行，但 `git config --get core.hooksPath` 没有
设置 —— 守卫从来没有被装上，一次都没运行过。**真阳性**，且没有任何症状：
推代码不会变红，出事那天才会发现。

**仓库 C `commitcorpus_test.go:22/34` — `skipped-test`（高危）**

`prs-*.jsonl`，这两个文件被 `.gitignore` 忽略、不在仓库里。开发机上有，
CI 和干净 clone 里没有 → 静默跳过。**真阳性。**

**仓库 D / 仓库 E / 仓库 F — `no-test-for-fix`（高危）**
三个仓库都有真实代码、零测试文件。仓库 D 有 1 个源文件

## 3. Dogfood 揪出的工具自身的 bug

这一节是这份文档最重要的部分。**上面那些仓库，不是全部一次就判对的。**

### 3.1 编译失败被当成「测试仍然绿」—— 最危险的一个

**现象**：仓库 A `⟨sha⟩` 最初被判成 **vacuous**（高危），报告写着
「撤掉修复后 36 个测试全部通过」，而同一份报告的证据栏里明明写着
`FAIL 仓库 A/link [build failed]` 和 `undefined: 那个新符号`。

**根因**：测试跑的是整个模块（`./...`）。`link` 编译不过，
旁边 20 个包照常通过；全局计数里「失败数 = 0」，于是被判成「仍然绿」。
**一个根本没跑起来的测试，被算成了通过。**

**修复**：两处。
1. 运行范围收敛到本次提交触及的包（源码文件 + 测试文件所在目录），
   计数和被审对象落在同一段代码上；
2. 只要出现任何构建错误，判定一律为「无法判定」（fail closed），
   不再因为别的包跑绿而被淹没。

**负对照**：夹具里放一个编译不过的包 + 一个正常通过的包，工具必须判
`coupled`。把这个修复改回去，测试立刻变红，并复现出
「1 个测试全部通过」与 `[build failed]` 并列的矛盾输出。

### 3.2 仓库没有测试运行器 → 直接报错退出

**现象**：仓库 E、仓库 F、仓库 D 跑 `--mode check` 只得到一行
`no supported test runner found`，退出码 2，什么发现都没有。

**根因**：CLI 在做任何检查之前就要求适配器。但静态体检读的是文件，
根本不需要测试运行器。

**修复**：`check` 模式不再依赖适配器；找不到运行器时，它本身成为一条发现
（「这个仓库有代码，但一个测试文件都没有」）。**最该被提醒的仓库，
原本恰恰是唯一没有输出的仓库。**

### 3.3 只加测试的提交被扣上「空洞」

**现象**：仓库 A `⟨sha⟩`（`test(storage): cover encrypted store`）被判成
vacuous —— 高危指控，说这个提交加的 21 个测试什么都没证明。

**根因**：这个提交只改了 `CHANGELOG.md` 和 `store_test.go`，**没改任何代码**。
没有修复可撤，反事实实验无从谈起。

**修复**：有测试但没有源码改动的提交，判定为 n/a，并降级为提示。想知道
「这个测试本身有没有效」，那是变异测试的活，不是这个工具的活。

### 3.4 改了注释和空白的提交被要求补测试

**现象**：仓库 A `⟨sha⟩`（`fix(bench): 修 vet 报错（冗余换行）`）被判
「改了代码但没有测试」。实际上它只是把 `fmt.Println("...\n")` 改成
`fmt.Print("...\n\n")`，输出完全一样。

**修复**：逐行比对 diff，去掉注释和空白之后完全一致的改动，判为
「没有改变行为」，不给它扣测试。同时按**单个文件**的改动量分级：改动
≤ 2 行的降为警告，大的才是高危。

### 3.5 「2026-10」被当成了文件路径

**现象**：仓库 C 多出 3 条高危 `skipped-test`，说跳过条件依赖
`ledger/2026-10` 和 `collect/me@example.com`。

**根因**：这两个都不是文件 —— 前者是月份键，后者是邮箱身份。工具把
**任何字符串字面量**都当成了路径候选。

**修复**：路径候选必须有文件的形状（有扩展名，或有分隔符且末段像名字），
并排除 URL、glob 和带 `@` 的字符串。修完之后这 3 条降为警告，
2 条真阳性保持高危。

### 3.6 绝对路径被解析成了仓库相对路径

**现象**：`/tmp/l.html` 被报成仓库里缺 `tmp/l.html`。

**根因**：`filepath.Join(root, "/tmp/l.html")` 会**吃掉前导斜杠**，
于是绝对路径被悄悄拼进了仓库根目录。

**修复**：绝对路径只在其真的位于仓库内部时才参与解析，否则直接放弃。

### 3.7 「断言被架空」和「守卫被跳过」被混成一件事
**现象**：仓库 A `cmd/seed/main.go:91` 被描述成
「错误被丢掉，断言却要求它是空的 —— 加载失败时这条断言照样通过」。

**根因**：那里根本没有断言。`if len(existing) > 0 { ...; return }` 是一段
保护性中止代码。工具的规则表只记了「比较方向」，默认假设被守卫的分支一定
是测试失败 —— 于是把两种形状混成了一种。

**修复**：从 AST 上判断被守卫的分支到底做什么，然后分开报告：

- 分支让测试失败 → 「断言被架空」（原措辞）
- 分支中止流程（`return` / `os.Exit`）→ 「一个本该拦住你的检查被跳过了」
- 分支只是打个日志 → **不报**（那是噪音，不是问题）

第三种情况配了负对照：只打日志的分支必须保持沉默。

### 3.8 第一个提交被甩出一条 git 原始报错

**现象**：CI 的 self-check（用 vacuous 审 vacuous 自己）报出一条
`coupled / 无法审计这个提交`，内容是 git 的
`fatal: invalid reference: 1cf10d6^`。

**根因**：仓库的第一个提交没有父提交，反事实实验没有基线。工具没有把
这件事当成「不适用」，而是让 git 的报错一路冒到了报告里。

**修复**：审计之前先用 `git rev-list --parents` 问一句「这个提交有父提交吗」。
没有的话，干净地判成 n/a 并给出一句话说明。

**这条不是 dogfood 揪出来的，是 CI 揪出来的** —— 工具审自己的时候，
才会遇到「只有一个提交」这种自己造出来的边界情况。

### 3.9 源码文件被塞给了测试运行器

**现象**：在真实 Python 仓库（仓库 I）上跑反事实审计时，命令是
`pytest ... src/<pkg>/api.py tests/test_client.py` —— 源码文件
也传给了 pytest。pytest 会把 `api.py` 当测试模块收集，于是报了一条
`ImportError while importing test module api.py`。

**根因**：Python 适配器把「本次改动的文件列表」原样交给了 pytest。
而那份列表里同时有源码和测试。Go 适配器没有这个问题（它把文件映射成
包模式），Python 和 Node 是直接传的。

**修复**：测试运行器只应该拿到测试文件。优先级也统一成 Go 那样 ——
包模式优先于文件列表；用文件列表时只取其中的测试文件。

**后果**：修之前那条 ImportError 看起来像「测试和修复耦合」，结论碰巧是对的，
但**证据是假的** —— 它来自工具自己传错了文件。一份靠错误理由得到正确结论的
报告，比一份明确说「不知道」的报告更危险。

### 3.10 交叉编译的二进制不能在本机执行

**现象**：release 工作流第一次跑就红了：4 个平台里 3 个失败，日志是
`./vacuous: cannot execute binary file: Exec format error`。

**根因**：job 在 amd64 Linux runner 上交叉编译，然后试图**执行** darwin/arm64
的二进制。二进制是好的，是检查方法错了。

**修复**：改用 `go version -m` —— 它读的是二进制里的构建信息，跨平台都能读，
能同时验证「这是个合法的 Go 可执行文件」和「它的 GOOS/GOARCH 确实是这个
job 要的平台」。只有 linux/amd64 那个 job 才真跑一遍。

**这条是唯一一个「不写代码、但用户装不上」的 bug**：它不在任何测试的覆盖
范围内，只有真的打一次 tag 才会暴露。

---

仓库 D 的工作树里有一份 仓库 C 源码的 untracked 副本
（`cmd/`、`go.mod`、`internal/`，逐字节相同）。这是**正在进行中的开发工作**，
不是数据泄漏。

它对 dogfood 数据有一个实际影响：那份多出来的 `go.mod` 让 Go 适配器认领了
仓库 D，于是「这个仓库零测试」这条发现消失了 —— 工具看的是磁盘上真实存在
的东西，它没有说错，是仓库的状态变了。上面的 仓库 D 数据取自一份

顺带验证了一件事：**工具不会往调用方仓库里写任何东西**。它的全部写操作只有
两处 —— 把生成物目录（dist/build/out/vendor/node_modules/static/public）复制进

### 3.11 本地 replace 依赖被判成「测试和修复耦合」

**现象**：在外部组织的那两个真实 Go 仓（仓库 G / H）上跑审计，全部提交都判成
`coupled（无法判定：测试和修复耦合在一起，拆不开）`。

**根因**：那两个仓的 `go.mod` 里有
`replace example.com/shared => ../shared` —— 依赖一个**同级
目录**。开发者的机器上有这个目录（软链到共享库 S 的真实目录），CI 里
也是 checkout 出来再 `ln -sfn` 建链。

而反事实 worktree 建在临时目录下，旁边没有 `../shared` → 编译失败 →
`replacement directory ../shared does not exist`。

工具把这条当成了耦合。**这是最坏的一种错**：把环境的错算到测试头上，
正是本项目存在的意义所反对的事。

**修复**（三处）：
1. 适配器新增一个**可选能力** `PrepareWorktree`：让语言适配器负责把
   「仓库之外的邻居」摆到 worktree 旁边。Go 适配器解析 `go.mod` 的 replace
   指令，把本地路径的依赖用软链摆到 checkout 旁边 —— 和 CI 干的
   `ln -sfn "$GITHUB_WORKSPACE/_shared" "$GITHUB_WORKSPACE/../shared"`
   是同一件事。
2. worktree 改成住在**自己的私有目录**里（`<tmp>/vacuous-XXX/repo`），
   邻居才有地方摆，而且两个并发运行不会抢同一个名字。
3. `replacement directory` 加进环境问题的特征表；环境判定改用**独立的
   kind**（`environment`），不再混在 `coupled` 里 —— 分类行说「coupled 2」
   而实际是 2 条环境问题，那是在骗人。

**验证**：修完之后，同样两个仓的判定从「耦合」变成「环境：检查出的代码缺
东西，跑不起来」，指向的是真实原因。

### 3.12 「CI 里没有测试步骤」被按 workflow 报，方向就是错的

**现象**：两个仓各报了 4 条「CI workflow 里没有任何测试步骤」。逐条核实，
其中 3 条是**误报**：

- `pr-test-policy.yml` —— 读 PR 描述、查文件列表的**策略校验器**，它本来
  就不该跑测试
- `wechat-merge-notify.yml` —— 发微信通知的
- `release-tag-guard.yml` —— 检查发布 tag 的

剩下那条（`prek.yml`）也有问题：它确实不跑测试，但这个仓的 `ci.yml` **跑
`go test`** —— 仓库的 CI 是有测试的。按 workflow 报，读者会得出完全相反的
结论。

**根因**：两个层面都错了。

1. 工具假设**每个 workflow 都应该跑测试**。
2. 更根本的：**这个问题问的是仓库，不是 workflow。**

**修复**：判定改成仓库级 ——
- 扫所有 workflow，**只要有一个跑测试，这个仓的 CI 就有测试**，一条都不报；
- 一个都不跑 → 报**一条**仓库级的发现，并说清楚它现在有什么检查
  （`它有这些检查：golangci-lint —— 能挡住语法和类型错误，挡不住「测试是空的」`）；
- 唯一保留的 per-workflow 发现是 `continue-on-error`：
  那个 job **确实跑了测试、然后把失败忽略了**。

**修完的结果**：admin **0 条发现**（它的 CI 确实跑测试），relay 1 条
（Google API 集成测试在没 key 时跳过 —— 合法的跳过，警告级）。

**教训**：判定的粒度要和**问题本身的粒度**一致。「这个仓的 CI 跑不跑测试」
是仓库级的问题，逐 workflow 回答它，答案必然是错的 —— 不是因为某条规则写
错了，而是因为问错了对象。

### 3.13 环境判定混用了 coupled 这个 kind

**现象**：分类行写 `coupled 2`，实际那两条是环境问题。

**根因**：环境判定复用了 `KindCoupled`。

**修复**：独立的 `environment` kind。这两件事在含义上是相反的：一个是
「测试和修复焊死了」，一个是「环境不全，谁也不知道」。混在一起，报告就会
在「测试有问题」和「我们没跑成」之间乱指。

### 3.14 编译错误在测试文件里 vs 在源码文件里，含义是相反的

**现象**：在 仓库 G 上审一个提交，编译错误全在**非测试文件**里
（`standardized.go` 引用了 shared 新增的 某视频模型 API），工具却判成
「测试和修复耦合」。

**根因**：`classify` 只看「有没有编译错误」，不看错误**在哪**。

**修复**：编译器错误读作 `path/file.go:12:5: message`，文件路径就在冒号前 ——
于是可以问适配器「这是不是测试文件」：

- 错误在**测试文件**里 → 测试依赖了这次修复引入的东西 → **coupled**
- 错误在**源码文件**里 → 父提交那份代码跟当前的依赖对不上了
  （shared 往前走了一步）→ **environment**

这是两件相反的事：一个是「测试和修复焊死了」，一个是「依赖动了，我们没跑成」。
以前只有一个 `coupled`，报告就会在两者之间乱指。

### 3.15 反事实 worktree 不会继承开发者本地的 go.mod 改动

**现象**：CI 的做法是

```
go mod edit -replace example.com/shared="$GITHUB_WORKSPACE/_shared"
go mod tidy
```

—— **CI 自己注入 replace**。提交在仓库里的 go.mod 根本没有 replace 指令。

所以：开发者的检出能编译（他手动跑过 `go mod edit`），反事实 worktree
（从提交的文件建出来的）**编译不过** → 每一条提交都判成环境问题，工具等于
没法用。

**修复**：`PrepareWorktree` 再多做一件事 —— 把**调用方 go.mod 里的 replace
指令继承到 worktree 的 go.mod 里**，并把它指向的目录摆好。调用方的文件
一个字都不动；改的是那个一次性的 worktree。

**「反事实树应该按调用方那棵树的方式编译」** —— 这是同一条原则的两面：
仓库之外的邻居要摆好，开发者手工加的本地设置也要继承。

### 3.16 模块路径被截断 —— 写出一个从来没人写过的 go.mod

**现象**：3.15 的继承机制把调用方 go.mod 里的 replace 指令抄进 worktree 的
go.mod。抄的时候，**模块路径**（`=>` 左边那一半）被 `TrimPrefix(old, "replace")`
无条件削掉了前缀。

**根因**：`replace` 这个词有两种身份。

1. **关键字**：`replace example.com/x => ../y` —— 开头那个 `replace` 是指令名，
   该被削掉。
2. **模块路径的一部分**：`replace.io/thing => ../thing` —— 一个合法的模块路径，
   以同样的字母开头，**不该被削**。

而在 **block 形式**里（`replace ( ... )`），每一行根本没有关键字：

```
replace (
	replace.io/thing => ../thing      ← 这一行没有关键字
	example.com/other => ../other
)
```

削完变成 `.io/thing` —— 一个不存在的模块。抄进 worktree 的 go.mod 之后，
那条 replace **指向一个没人发布过的模块**，于是替换**静默地不再生效**。
更糟的是这个 go.mod 本身语法合法（`go mod edit -json` 照收不误），所以
没有任何报错 —— 失败会推迟到很久以后，以「依赖解析不到」的形式出现，
跟真正的病因隔了三层。

**修复**：只有当 `replace` 后面跟的是空白时，它才是关键字：

```go
if rest, ok := strings.CutPrefix(old, "replace"); ok {
	if rest != "" && (rest[0] == ' ' || rest[0] == '\t') {
		old = strings.TrimSpace(rest)
	}
}
```

block 形式的那一行没有空格 → 不削；`replace example.com/x => ...` 有空格 →
削。两条都对了。

**负对照**：拿修好的测试去跑**没修的代码**，三条全红：

- `replace.io/thing` 解析成 `""`（实际 map 里是 `.io/thing`）
- worktree 的 go.mod 里出现 `replace .io/thing => ../thing`
- 版本 pin 被继承（见 3.17）

### 3.17 版本 pin 被继承 —— 反事实树用错了依赖版本

**现象**：3.15 的继承机制把调用方 go.mod 里的 replace 指令**全部**抄进
worktree 的 go.mod，包括这一种：

```
replace example.com/x => example.com/x v1.0.0
```

**根因**：继承的分界线画错了。3.15 想继承的是**本地环境设置** ——
「我本地必须跑 `go mod edit -replace` 才能编译」—— 但版本 pin 不是环境设置，
是**依赖决策**：它把某个模块钉死在某个版本上。

被判定的那条提交，是**照着它自己当时的依赖版本写的**。继承 pin 等于让反事实
树用**调用方那个版本**去编译它 —— 于是「撤掉修复后测试还绿不绿」这个问题，
是在**错误的依赖版本**下回答的。

**方向反了，而且反在最坏的方向**：版本一变，行为就可能变，而新版依赖通常
**更宽容**（或者恰好绕过了那个 bug）。于是反事实跑绿 → 工具判「vacuous」
→ 报一条**高危**的「这个测试什么都没测到」。

**这个工具的全部意义就是抓这一类**。它自己在反事实里引入了一个会藏 bug 的
变量。

**修复**：只有**目录**目标被继承（`./x`、`../x`、绝对路径）。

绝对路径**必须**继承 —— CI 注入的就是绝对路径：

```
go mod edit -replace example.com/shared="$GITHUB_WORKSPACE/_shared"
```

这一条有专门的测试守着（「绝对目录目标仍然被继承」），防止修过头把真正要
继承的东西一起扔掉。

**负对照**：修之前那条测试是红的 —— worktree 的 go.mod 里出现了
`replace example.com/shared => example.com/shared v1.0.0`。

> **2026-10-20 21:xx 复核**：这一轮把 3.16/3.17 的负对照**重新做了一遍**，
> 而且用的是更严的做法 —— 只把**行为**改回旧的，函数签名留着。
> 只把整个文件退回去的话，测试是**编译不过**（`undefined: parseReplaces`），
> 那只能证明「测试依赖新代码」，证明不了「三条断言分别抓得住各自的病」。
>
> | 拆掉的修复 | 变红的用例 | 症状 |
> |---|---|---|
> | 3.16 的解析 | `TestParseReplacesKeepsAModulePathThatStartsWithReplace` | `replace.io/thing` 被解析成 `.io/thing` |
> | 3.16 的解析 | `TestPrepareWorktreeWritesTheModulePathUnchanged` | worktree 的 go.mod 里的模块路径被写坏了 |
> | 3.17 的版本 pin 过滤 | `TestPrepareWorktreeDoesNotInheritAVersionPin` | 版本 pin 被继承进反事实树 |
>
> 防修过头的那条（`TestPrepareWorktreeStillInheritsAnAbsoluteDirectoryTarget`
> —— 绝对目录目标仍然被继承）全程保持绿。

### 3.21 闸门可以悄悄瞎掉 —— record 把被审仓名单写空了

**这一轮闸门报的是「无变化」，CI 也是绿的。按流程本来该收工。我没收工** ——
因为闸门本身就是「判有没有新东西」的那把尺子，一把自己会坏的尺子，报什么都不算数。

复核闸门本身的负对照时（不是复核工具），撞上一个**假阴性**：闸门再也不看任何
一个被审仓库了，而它的输出是 `NO CHANGE`、退出码 0 —— 跟「一切正常」长得
一模一样。

**根因**：`record` 接受 `-target`，但不校验它。

```
scripts/gate.sh record -yes            # 少写了 -target
```

写入的状态是 `targets: null`。`Check` 只遍历 `st.Targets` —— 空名单 = 一只眼睛
都没了，剩下「工具代码变没变」那一只。**被审仓库往前走了几步，闸门看不见。**

少写一两个也一样：名单从 6 个变成 5 个，那一个仓就悄悄从视野里消失了。

危险的地方在于**没有任何症状**：退出码 0、输出 `NO CHANGE`、CI 绿、闸门自己不
报错。唯一能看出问题的时刻，是「该跑的那一轮没跑」—— 而那已经过去很久了。

这跟 3.18 是同一个病根的两面：3.18 是基线每次都自己失效（一直喊「有变化」），
3.21 是名单被写空之后一直喊「没变化」。**一个吵死人的闸门和一个瞎掉的闸门，
坏起来是同一个形状 —— 都是信号跟现实脱钩了。**

**修复**：在写入的那一刻挡住。

`gate.ValidateRecordTargets(old, new, force)`：

- 一个都不记 → 拒绝（退出码 2，状态文件不写）
- 比上次少了 → 拒绝，并**点名是哪个仓**（退出码 2，状态文件不写）
- 确实要放弃盯某个仓 → `--force`，而且要把丢掉的名字打印出来

**负对照**：

| 拆掉的修复 | 变红的用例 | 保持绿 |

| record 的名单校验（命令层） | `TestRunRecordRefusesToWriteAStateWithoutTargets`、`TestRunRecordRefusesToDropAWatchedTarget` | `TestValidateRecordTargetsAllowsSameOrMore`（正常用法不被拦） |
| 策略函数本身 | `TestValidateRecordTargetsRefusesEmptyList`、`TestValidateRecordTargetsRefusesSilentDrop` | 同上 |
| 校验逻辑整个抽掉 | 上述 4 条一起红 | — |

| `record -yes` 只写 5 个 | 拒绝，退出码 2，点名 仓库 F |
| `record -yes` 写全 6 个 | 成功，退出码 0 |
| `record -yes --force` 只写 1 个 | 允许，并把丢掉的 5 个名字打出来 |

### 3.22 「判不出来」的退出码和文档对不上

**现象**：文档里写着 `check` 的退出码是 `0=没变 / 1=变了 / 2=判不出来`，
但 `runCheck` 里所有非空变更一律 `return 1` —— `Change{Kind:"unknown"}`
（「判不出来」）也走 1。

**根因**：退出码是手写的 `return 1`，没把「判不出来」这一类单独分出来。
只有状态文件读不出来的时候才返回 2。

**为什么值得修**：1 和 2 在调用方那里的处理方式**不一样** —— 1 是「变了，去查」，
2 是「判不出来，这轮结果不能当准，得再跑一次」。分不开的时候，
「被审仓临时读不到」（目录被挪了、权限掉了）会被报成「变了」，
人和定时任务都会把它当成一次真实的变化 —— 而它其实什么也没说。

**修复**：`gate.ExitCode(changes)` —— 有任何一条 `unknown` 就返回 2，否则 1，空则 0。

**负对照**：

| 拆掉的修复 | 变红的用例 |
|---|---|
| ExitCode 区分 unknown | `TestExitCodeDistinguishesUnknownFromChange`、`TestRunCheckExitCodes` |

### 3.23 闸门看不见「改了没提交」的改动 —— 工作树脏了它也报 NO CHANGE

**这一轮闸门报的是「无变化」，CI 也是绿的。按流程本来该收工。我没收工** ——
上一轮刚改过闸门自己的代码（`1eab192`），它的「没变化」是新代码的断言，
验它比信它便宜。

复核这把尺子（复核的是闸门，不是工具）时，撞上一个**假阴性**。

**现象**：改了代码但**没提交**，闸门照样报 `NO CHANGE`、退出码 0。

```
$ scripts/gate.sh check
NO CHANGE
```

为什么这要命：核验跑的是**工作树**里的代码，CI 跑的是 **HEAD** 里的代码。
三者不是一份的时候，闸门报「没变化」就是在说谎 —— 而且是说得很像真的那种谎：

1. 闸门说「没变化」→ 这一轮不跑完整核验；
2. 那份改动因此永远不被核验、也不会被提交；
3. 下一轮改到同一个文件时把它覆盖掉 —— 谁也不知道它曾经存在过。

症状和 3.21 一模一样：**没有任何症状**。`NO CHANGE`、退出码 0、CI 绿。

**根因**：`Fingerprint()` 用 `git ls-tree -r HEAD` —— 量的是**已提交**的内容。
闸门从来没有看过工作树。

这跟它自己注释里的话是矛盾的：注释写的是「改代码指纹就变」，但实现里
「改代码」等于「提交了代码」。**改了没提交，等于没改** —— 对 HEAD 来说确实
没改，可对**要跑核验的那份代码**来说，它改了。

同族还有一个洞：**新文件忘了 `git add`**。本地核验跑的是工作树（含这个新
文件），CI 跑的是 HEAD（不含它）—— 两份代码，核验结论却只对其中一份成立。

**修复**：`gate.DirtyPaths()` —— 用 `git status --porcelain -z` 把工作树里
「改了没提交」和「没被跟踪」的路径捞出来，`Check()` 据此报一条
`Kind:"dirty"` 的变更（退出码 1，和「代码变了」同一处理）。

三条边界，都是为了不把闸门变成「吵死人的闸门」：

- **文档脏了不算数**：改文档不影响工具跑出来的结果，每轮都因为它重跑，
  就是 3.18 那个自毁的毛病换个姿势复发。
- **被 `.gitignore` 忽略的文件不算数**：编译产物、覆盖率文件、临时目录，
  它们每天都在那儿，触发就等于闸门永远在响。
- **只看工具自己的仓库，不看被审仓库的工作树**：仓库 D 的工作树里一直有
  用户正在开发的未提交源码，把它算进去，闸门就每一轮都喊「有变化」——
  正是 3.18 的病根。被审仓库的工作树由工具自己的审计去报（那种情况会被
  报成高危，见任务说明里的「已知情况」）。**这条是有意的取舍，不是漏掉。**

**负对照**：

| 拆掉的修复 | 变红的用例 | 保持绿 |
|---|---|---|
| `Check()` 里的 dirty 检查 | `TestCheckReportsUncommittedCodeChange`、`TestCheckReportsUntrackedSourceFile` | — |
| 同上（命令层） | `TestRunCheckReportsUncommittedChange` | — |
| dirty 检查整个抽掉 | 上面 3 条一起红，报的正是生产症状：「却报了 0 条」 | `TestCheckIsQuietWhenOnlyDocsAreDirty`、`TestCheckIsQuietWhenUntrackedFileIsIgnored`（不该吵的时候不吵） |

抽掉之后跑出来的那句红：

```
--- FAIL: TestCheckReportsUncommittedCodeChange
    gate_test.go:342: 改了没提交应该报 1 条，却报了 0 条: []
```

**现场验证**（真仓，不是夹具）：修完在真仓里跑一次，闸门认出了工作树里
那 3 个文件：

```
$ scripts/gate.sh check
CHANGED:
  - [dirty] 工具代码有未提交的改动（3 个文件）：internal/gate/cmd/gatecheck/main_test.go、internal/gate/gate.go、internal/gate/gate_test.go
exit=1
```

提交之后（工作树干净）再问一次，闸门重新安静下来 —— 这条也一起验了。

### 3.20 一行改动也能被判成「高危：这个测试什么都没测到」

**现象**：修完 3.19 之后，仓库 C（7 个 module，一直没被审过）第一次能审了，
审出来 1 条**高危**的 `vacuous-test`，指着 `collect/collect_test.go`。

人工核实之后：**这是误伤**。

那笔提交做的是三件事：把一个版本号常量从 `0.2.0` 改成 `0.1.0`、把注释里的
一个项目名脱敏、把测试里的真项目名换成假名。**代码那边一共改了 2 行**（一行
删、一行加）。

反事实跑出来是「16 个测试全部通过」—— 因为版本号根本不是测试该管的东西。

**根因**：工具对「没有测试看着这次改动」这件事，**分两种情况用了两套音量**：

| 这笔提交 | 判定 |
|---|---|
| 改了代码，**没带**测试 | ≤2 行 → **警告**；再大 → 高危 |
| 改了代码，**碰了**测试文件 | **一律高危** |

同一个 2 行的改动，只因为提交顺手动了测试文件，就从「警告」跳到「高危」。

**为什么这算误伤**：这条发现的措辞是「这个测试……从来没有看守过这个行为」，
而且**指着那个测试文件**。人读到之后合理的结论是「这个测试文件是空的」——
而它不是。那个测试文件里每条规则都配了负对照，是这个仓里质量最高的一批测试
之一。工具拿一笔版本号提交去指控它，是把话说错了。

**修复**：用同一把尺子。

「没有测试看着这次改动」在改动很小时多半不是问题 —— 版本号、消息文案、
改个措辞都属于这一类。所以 `vacuous-test` 的严重级别现在也看**改动有多大**：
≤2 行 → 警告，并且把措辞改成实话（「改动很小，没有测试看着它 —— 多半不是
问题」）；再大 → 仍然是高危。

**这条改动只会让工具少报，不会让它多报**：真正该抓的「大改动 + 测试不红」
一点没动（`TestAuditDetectsVacuousTest` 仍然要求高危）。

**负对照**：

| 拆掉的修复 | 变红的用例 | 保持绿 |
|---|---|---|
| 小改动降级 | `TestAuditDoesNotAccuseATinyChange`（夹具：一行版本号 + 碰了测试文件） | `TestAuditDetectsVacuousTest`（真的空洞测试仍然是高危） |

真实仓库复核：同一条 仓库 C 的发现，从「高危」变成「警告」，措辞也换成
了实话。

### 3.19 有嵌套 module 的仓库，根 module 根本没跑 —— 判决是凭空来的

**现象**：2026-10-20 21:xx 用工具审它自己那个提交（`f7113e9`，加闸门那笔），
出来的结论是「environment：检查出的代码缺东西，跑不起来」，INFO 级。

不合理的地方有三层，一层比一层严重：

1. 这笔提交在**根 module** 里，根 module 的测试完全能跑；
2. 手工复现（父提交建树 → 只打测试补丁 → `go test ./internal/gate/...`）拿到的
   是**编译错误**（`undefined: Fingerprint`）—— 那是「耦合」，不是「环境」；
3. 拿另外三笔提交重审，全是「environment」。

**根因**：`runInModules` 只在**嵌套 module** 里跑计划，**根 module 被跳过了**
—— `findModuleRoots` 只返回嵌套的那些（`rel == "."` 直接跳过）。

于是：

- 根 module 的测试**一次都没跑过**。跑的是 `internal/adapters/testdata/` 底下
  那些夹具 module。
- 判决是拿夹具 module 的结果推出来的。这个仓的夹具里有一个
  `goproj-broken`（故意编译不过），于是一笔提交只要碰了根 module 的代码，
  工具就可能报一条**高危**的「这个测试什么都没测到」—— 而被审的那份测试
  恰恰**测到了**。
- 范围（`./internal/gate/...`）是**相对根 module** 算的。拿到嵌套 module 里
  一跑，go 报 `lstat ./internal/gate/: no such file or directory` —— 这是工具
  自己造出来的错，`isEnvironmentFailure` 认得这个串，于是判成「环境问题」，
  把根 module 本来能给出的结论冲掉了。

**这个工具的全部意义是「判决必须来自真的执行」。这里判决来自一次根本没发生
的执行。**

**为什么一直没人发现**：6 个被审仓里 仓库 A / 仓库 B / 仓库 E / 仓库 F 都是
单 module，仓库 C 有 7 个 module 但只跑过 `--mode check`。而**这个仓
自己**有 4 个嵌套 module（testdata 夹具）—— 也就是说，CI 里那个
`vacuous --mode audit --fail-on critical` 的 self-check job，**从第一天起就
是装饰品**：它审的每一笔提交都是 environment，INFO 级，`--fail-on critical`
永远不可能触发。

**修复**（`internal/adapters/modules.go`）：

1. **根 module 先跑**，它的结果才是判决的依据。嵌套 module 排在后面。
2. **范围之外的 module 直接跳过**。范围是相对根 module 算的，在别的 module
   里本来就什么都不指向；在那儿跑只会造出「lstat: no such file」这种自造的
   错。判断方式是先用 `go list <范围>` 问那个 module 有没有这些包；只有
   「找不到」这一种失败算跳过，别的失败照旧暴露（fail closed）。

**负对照**：两个夹具，两个拆法。

| 夹具 | 形状 | 拆掉修复后 |
|---|---|---|
| `MultiModuleFixture` | 代码在仓库根，嵌套 module 有自己的绿测试 | 根 module 不跑 → 只剩嵌套 module 的绿测试 → **判成「vacuous」**（高危误伤） |
| `MultiModuleScopedFixture` | 代码在 `app/` 子目录（范围是 `./app/...`） | 范围照跑所有 module → 嵌套 module 报 `lstat ./app/: no such file` → **判成「environment」**（有结论却不说） |

两个拆法分别变红、互不干扰，说明两个测试盯的是两半，不是同一个现象。

**修完之后**，同样三笔提交的结果从「environment」变成了真结论：
`f7113e9` / `36741f3` / `979bb52` → **coupled**（撤掉修复后测试编译不过），
`3ad45de` → **proven**（测试真的守住了那个行为）。

### 3.18 闸门把自己弄失效了 —— 每轮都误报「有变化」

**现象**：定时校验任务的变更检测闸门，每一轮都报「有变化」。

2026-10-20 21:15 那一轮核验完，文档里记下「基线 commit: df223ea」，然后又提交了
一份文档（`1bbe413`，只因为那份文档补了 6 个被审计仓库的 HEAD）—— 基线没跟着
更新。21:17 那一轮一看：基线 `df223ea` ≠ HEAD `1bbe413` → 「有变化」→ 重跑完整
的六仓 dogfood。而这期间**代码没动、被审的 6 个仓一个都没动、CI 全绿**。

**根因**：基线量的是「最后一次核验时的 commit 是谁」，而**每一轮核验自己产生的
提交**都会改变这个量。基线在写下的那一刻就注定要过期。

更要命的是它把信号毁掉了：闸门每轮都喊「有变化」，于是「没变化」这件事永远
观察不到。一个每轮都误报的闸门等于没有闸门 —— 该跑的时候跑，不该跑的时候
也跑，跑完什么新东西都没有，还要再提交一份文档把基线再弄失效一次。

这正是「**宁可漏报不可误伤**」那条原则的另一个版本：误伤会让人给它加
`--no-verify`，闸门就等于不存在。

**修复**：基线改成**代码的指纹**。

- 指纹 = HEAD 上除 `docs/` 和 `*.md` 之外所有被跟踪文件的内容哈希
  （`git ls-tree` 的输出，里面带着每个文件的 blob 哈希）。
  改文档不改指纹；改代码、改 CI 配置，指纹就变。
- 状态文件放在 `.git/vacuous-gate.state`：**它是这份 clone 的状态，不是仓库的
  内容**，所以写它本身不产生提交，也就不会再把基线弄失效。
- 「判不出来」和「没变化」必须分得开：状态文件缺失、损坏、被审仓库读不到
  HEAD，一律按「有变化」处理（退出码 2），不报成「没问题」。

**闸门本身也是代码，所以它也有负对照**（`internal/gate/gate_test.go`）：

| 场景 | 期望 | 把修复拆掉之后 |
|---|---|---|
| 只改文档再问一次 | 没变化 | **报「工具代码变了」**（红灯） |
| 改代码 | 报「代码变了」 | — |
| 被审仓库往前走一步 | 报「被审仓库动了」 | — |
| 被审仓库没了 | 报「判不出来」 | — |
| 状态文件缺失 / 损坏 | 报「判不出来」 | — |
| 写完状态之后 | 工作树必须干净、HEAD 不动 | **工作树里多出状态文件**（红灯） |

两个拆法：

1. 把 `isDoc` 改成永远返回 false（退回「文档也算代码」）→ 两条用例变红，
   报的正是生产上那条症状：「工具代码变了」。
2. 把状态文件放回仓库工作树 → 两条用例变红：工作树被弄脏，而且因为状态
   文件进了工作树，指缀也跟着变。

**顺带修掉的两个真 bug**（写闸门时踩到的，都有自己的负对照）：

1. `git rev-parse --absolute-git-dir` 的输出带换行，没削掉就拼进路径 →
   状态文件路径里夹了个换行符，写文件时报「目录不存在」—— 一个看起来毫不
   相干的错。
2. `go run` 会把程序的退出码吃掉（子程序非零退出时，go 自己返回 1 并打印
   `exit status N`），而 0/1/2 这个区分正是闸门的契约。所以脚本改成先编译
   再执行。

### 3.24 合并提交被当成「一次改动」去指责

**现象**：在九个真实仓库上做全量测量时，`no-test-for-fix` 这类发现里有 4 条
落在**合并提交**上。

**根因**：合并提交拿第一个父提交当基线去 diff，等于把**整个分支**的改动
都算到这次合并头上。分支上那些提交明明各自都审过了，合并的时候又被审一遍。

**后果不是学术问题**：一个合并频繁的仓库上，**每一次合并**都会被报成
「改了代码但没有测试跟着」—— 闸门等于什么都合不进去。

**修复**：审计之前先问「这个提交有几个父提交」。两个以上就是合并提交，
判成 n/a 并说明「里面的改动在分支的各个提交里已经审过了」。

**怎么发现的**：不是靠读代码，是靠**在九个真实仓库上跑一遍全量测量**，
把每条发现回查一遍它落在哪种提交上。合并提交是量出来的，不是想出来的。

### 3.25 豁免后门在 audit 模式下根本没接上

**现象**：在 `audit` 模式里，在工具报出来的那一行上写 `// vacuous:ignore`，
**一点用都没有** —— 发现照样报出来。同一行注释在 `check` 模式下却好使。

**根因**：audit 模式产出的发现**只带文件名、不带行号**（`File` 有值，`Line`
永远是 0）。而豁免器是靠行号找注释的：它先看「这一行」，再看「上一行」。
行号是 0，两个分支都进不去 → 一条都豁免不了。

**后果不是边角问题**：这个后门**就是为了 `no-test-for-fix` 建的**（那一类
大约三成是重构 / 改错别字 / 删死代码）。而在 audit 模式里，`no-test-for-fix`
恰恰**全部**带不上行号 —— 后门在它唯一要解决的那一类上完全失效。
`check` 模式能用的那两类（`discards-error`、`skipped-test`）都带行号。

**修复**：豁免器补一条规则 —— **只给了文件、没给行号**的发现，文件里任何
一行**独立注释行**上的标记都算数。

带行号的发现**不吃**这条规则。否则文件顶上放一个标记，整个文件的发现都会
被吞掉 —— 一个文件可以有好几条发现。

**负对照**：三条。① 文件里有独立注释行 → 豁免；② 文件里只有**行尾**注释
→ 不豁免（行尾注释是关于它自己那一行的）；③ 标记在文件别处、发现自带行号
→ 不豁免（精确性没丢）。

### 3.26 豁免读的是工作树，不是被审的那个提交

**现象**：审计一个**旧提交**时，工作树里后来加的 `// vacuous:ignore`
会把那个旧提交的问题一起吞掉。

**根因**：豁免器一直从**工作树**读文件。可是 audit 审的是某个提交 ——
连反事实实验都是在那个提交的检出目录里跑的。只有豁免这一项去看工作树，
读的就不是同一个版本。

**后果**：一条**当时确实存在**的问题，因为今天有人在工作树里补了一句注释，
就从报告里消失了。这是在**藏问题**，比误报更糟。

**修复**：audit 模式按**被审提交**的版本读文件（`git cat-file` 那个提交上的
内容）。`check` 模式不变 —— 它审的就是工作树。

于是规则说得通了：**注释是那笔改动旁边的记录**。想豁免一笔历史提交，就在
那一笔里写下理由；今天在工作树里补一句，管不到它。

**负对照**：一个仓，三个提交 —— 第二笔改了行为没写注释，第三笔才补上注释。
审第二笔 → 问题照报（它自己没有注释）；审第三笔 → 被豁免。

### 3.27 逗号写法把豁免范围放大成「所有类别」

**现象**：`// vacuous:ignore no-test-for-fix,skipped-test`（逗号后**不加**
空格）会把**所有**类别都豁免掉。写成 `no-test-for-fix, skipped-test`
（逗号后**加**空格）就正常。

**根因**：原来只按空格切词。`no-test-for-fix,skipped-test` 是**一个**词 →
不是已知类别名 → 当成「理由」→ 而规则是「理由 = 豁免所有类别」。
一个空格的差别，豁免范围从两类变成全部。

**修复**：按逗号**和**空白一起切词。切出来的词**全是**已知类别名 → 只豁免
这些；否则算理由 → 豁免全部。方向是往窄了改 —— 写错一笔只会少豁免，
不会多豁免。

**负对照**：`no-test-for-fix,skipped-test` → 这两类被豁免，第三类
（`discards-error`）不被豁免。

### 3.28 豁免掉的发现仍然被算进统计，报告自相矛盾

**现象**：豁免之后报告里**一条发现都没有**，但统计行写着「无测试 1」，
JSON 里写着 `"no_test": 1` 而 `"findings": []`。

**根因**：判决计数（proven / vacuous / 无测试 / 无法判定）是在**豁免之前**
加的。

**后果**：一份自相矛盾的文件。`"no_test": 1` 配 `"findings": []`，
读的人没法判断「有一条发现被藏起来了」还是「统计写错了」。一个会自相矛盾
的报告，没资格当闸门。

**修复**：被豁免的发现**不再计入统计**。豁免的理由没有丢 —— 它写在代码旁边，
下一个人想不通「为什么闸门放过了这条」的时候，会先看代码。

**负对照**：豁免一条之后，JSON 里必须同时是 `"no_test": 0` 和
`"findings": []`。

### 3.29 只改了注释的提交，只要同时碰了测试文件就被扣成「空洞测试」

**现象**：同一个**只改注释**的提交，判定结果取决于它有没有顺手碰过测试文件：

| 提交 | 判定 |
|---|---|
| 改注释，没碰测试文件 | 「这个改动没有改变代码的行为」✅ |
| 改注释，**同时**碰了测试文件 | 「这个测试在撤掉修复后依然是绿的」❌ |

**根因**：3.4 那条「改动只是注释和空白」的规则，被放在了
`if len(TestFiles) == 0` **里面** —— 只有**没碰测试文件**的提交才会走到那条路。
碰了测试文件的提交直接冲进反事实实验。

**后果**：把注释撤掉，测试当然还是绿的 —— **注释没有行为可以破坏**。
拿「测试有没有变红」去问一笔只改了注释的提交，问题本身就没有答案。
而工具拿这个没有答案的问题，得出了「这个测试什么都没测到」的结论。

这不是理论上的问题：**这个仓自己就中招了**。它自己的 `docs: 脱敏` 那笔
提交只改了一行注释（外加改了一句测试里的路径），被工具判成了「空洞测试」。
工具审自己审出了自己的误报。

**修复**：把这条规则从 `if len(TestFiles) == 0` 里**提出来**，放到所有提交
都要过的地方 —— 判的是**源码改动**，不是文件列表。

**负对照**：一个只改注释、同时碰了测试文件的提交 → 判 n/a，不是空洞测试。
把修复改回去，测试立刻变红，并复现出「空洞 1」。

### 3.30 默认的审计窗口被一行 `fs.IntVar` 弄没了 —— 工具审的是全部历史

**现象**：仓库 A 有 35 个提交。工具报告说它审了**最近 20 个提交**，但统计
加起来是 35：

```
统计: proven 3 · vacuous 0 · 无测试 9 · 无法判定 7 · 不适用 16
按类别: coupled 7 · no-test-for-fix 12 · not-applicable 1
```

3 + 9 + 7 + 16 = **35**。报告自己说「最近 20 个提交」，数字却是 35 ——
**报告自相矛盾**。

**根因**：`flag.IntVar` 在注册的那一刻就把默认值写进了它绑定的变量。于是

```go
opts := &Options{ Limit: 20, ... }          // ← 想要 20
fs.IntVar(&opts.Limit, "limit", 0, "...")   // ← 立刻覆写成 0
```

而 `0` 的含义是「不限制」→ **审整条历史**。README、flag 帮助、代码注释
里写的「默认审最近 20 个提交」，全部是一句空话。

**为什么这么久才被发现**：仓库 A 之前正好只有 20 个提交。窗口是 20、仓库也是
20，两边撞上了，看不出差别。等仓库长到 35 个提交（多出来的 15 个全是
2026-07 的老提交），多审的那 15 个就变成了报告里指向几个月前提交的指控。

**后果**：① 工具审的是没人要审的历史 —— 报告里点名的 `f429b1d`、`0dbfbe8`
都是 7 月的提交；② **CI 的 self-check 每次 push 都在审全部历史**，仓库越长
越慢；③ 在 仓库 G（685+ 提交）/ 仓库 H（785+ 提交）那种规模上，
「审全部历史」意味着几百次反事实执行。

**修复**：默认值从结构体取，不写字面量 ——
`fs.IntVar(&opts.Limit, "limit", opts.Limit, ...)`，和相邻的 `Mode` /
`FailOn` / `Timeout` 写法一致。

**负对照**：`parse([]string{})` 必须拿到 `Limit == 20`。把修复改回字面量 `0`，
测试立刻变红，并复现出「default audit window = 0, want 20」。

### 3.31 「怎么自己验一遍」的配方没有重建工具自己那棵树

**现象**：报告里每条结论都附了一段「怎么自己验一遍」的命令。那段命令说
「逐字跑通过 —— 输出和工具看到的完全一样」。在仓库 A 的 `b5f99ab` 上
**跑不通**：

```
fatal: path 'internal/link/engine.go' exists on disk, but not in 'b5f99ab^'
```

**根因**：工具的反事实树是**「父提交 + 测试侧的改动」**；配方搭的是
**「这次提交 + 父提交版本的源文件」**。两者在两种情况下不是同一棵树：

| | 工具的树 | 旧配方的树 |
|---|---|---|
| 这次提交**新建**的源文件 | 不存在（父提交没有） | `git show` 失败，shell 的 `>` 把它**截成 0 字节** |
| 非源文件（`go.mod`、`go.sum`、配置） | 父提交的版本 | **这次提交的版本** |

0 字节的源文件不是「没有这个文件」—— 它让编译以另一种方式失败：

| | 工具看到的 | 旧配方跑出来的 |
|---|---|---|
| 仓库 A 的 `internal/link` 的 FailedBuild | 仓库 B 的 `internal/storage` | 仓库 A 的 `internal/link` |
| 报错 | `package 仓库B/internal/storage is not in std` | `expected 'package', found 'EOF'` |

**后果**：这条配方存在的意义就是「不信我就自己查」。它给的是**另一次实验**，
读者查出来的东西和工具说的不是一回事 —— 而读者会以为是自己查错了。
比没有配方更坏。

**修复**：配方照着工具的做法搭树 —— **归档父提交，再把测试侧的补丁打进去**，
别的什么都不做：

```bash
git archive <sha>^ | tar -x -C /tmp/vac-verify
git diff --binary <sha>^ <sha> -- '<测试文件>' > /tmp/vac-verify-tests.patch
cd /tmp/vac-verify && git apply --whitespace=nowarn /tmp/vac-verify-tests.patch
```

新建的文件父提交里根本没有，所以自然不在树上；`go.mod` 之类自然就是父提交
的版本。两处偏差一次性消失。

**负对照**：真跑一遍配方，然后逐条比树 —— 新建的源文件必须**不存在**、
测试文件必须**在**、`go.mod` 必须等于父提交那份、测试必须以
`undefined: Value` 失败（而不是 `expected 'package', found 'EOF'`）。
把修复改回去，四条断言同时变红，并复现出上面那张对照表。

### 3.32 一致性自检只看了输出尾部 4KB —— 大仓上工具全部不敢下结论

**现象**：在一个 Go 服务仓上做反事实审计，8 个提交里冒出
**3 个 `contradictory`**（工具自相矛盾），证据写着「结论说有测试变红了，
但运行器自己的输出里没有失败」。而同一份证据里的计数是
**733 通过 · 42 失败** —— 明明有 42 个失败，工具却说自己的输出里没有失败。

**根因**：一致性自检要在运行器的**原始输出**里找失败标记（`FAIL` /
`build failed` / `panic:`）。而适配器只保留了 stdout 的**尾部 4000 字节**
（`tailOf(stdout.Bytes(), 4000)`）。`go test -json` 是边跑边打的：733 个
通过的测试事件把失败标记顶出了这个窗口。自检在窗口里没看见 `FAIL`，于是
判定「结论和输出矛盾」。

**后果是最严重的一种**：这个自检本来是工具的**最后一道安全网**（3.14、4.1 ❺
两轮都靠它兜底）。它一误报，工具就在**每一个大仓上全部拒绝下结论** ——
不是给错答案，是什么都不给。而失败的仓恰恰是测试最多的仓，也就是最该被审的仓。

**根子上的问题**：`RawOutput` 全仓**只被这一处自检用**。那 4000 字节的截断
没有任何别的用处，纯粹是在破坏这个自检。

**修复**：`RawOutput` 继续做**给人看**的尾部（保留 4KB 就够），另外加一个
字段 `RawFailed bool` —— **对完整输出**扫一遍得出的「有没有失败」标记。
自检改用这个字段。失败标记的判定逻辑（`core.MentionsFailure`）挪到 `core`，
适配器和引擎共用一份，不会各说各话。

**负对照**：构造一份 8KB 的输出 —— **失败在最前面**，后面全是通过的包
（这正是 `go test -json` 的真实形状）。把修复改回旧的 4KB 窗口写法，
测试立刻变红（`consistency_test.go` 里那条回归测试）；改回来，绿。

> 顺带一条：这条回归测试的**第一版夹具写错了** —— 我把失败放在输出末尾，
> 而末尾正好在尾部窗口里，于是负对照没变红。是纪律逼我回去看「测试为什么
> 没红」，才发现夹具根本没复现真实形状。**夹具必须复现真实形状，否则负对照
> 是假的。**

### 3.33 Go 模块解析失败被判成「测试和修复耦合」—— 让测试替环境背锅

**现象**：一个仓的编译错误是
`pkg/widget_test.go:12:2: module lookup disabled by GOPROXY=off`。
工具判成 **coupled**（测试和修复缠在一起），而不是 environment。

**根因**：环境判定的**模式表**里没有 Go 模块解析失败这一类。表里只有
「文件不存在」「replacement directory」这些通用形状。而错误里**点名了测试
文件** —— 走的是「编译错误在测试文件里 = 耦合」那条分支。

**后果**：这是本项目最贵的一种错判。coupled 的字面意思是「**你的测试依赖了
这次修复引入的东西**」—— 读者读到之后，下一个动作是**去改一个本来没问题
的测试**。而真相是「这台机器上没有这个依赖」。

**修复**：模式表补上 Go 模块解析失败的形状（`module lookup disabled`、
`no required module provides package`、`missing go.sum entry`、
`cannot find module`、以及连不上代理的 `dial tcp` / `i/o timeout` /
`connection refused`）。这些字符串**只有 Go 会打**，不会误伤 Python / Node。

**负对照**：① 三种模块解析失败（错误里点名了测试文件）→ 判 environment；
② 把模式表里 Go 那几条**抽掉**，判定必须**翻回 coupled**（证明是这张表在
起作用，而不是碰巧走了兜底分支）；③ 一个表里没有的真编译错误
（`undefined: NewThing`，在测试文件里）→ 仍然判 coupled（**不能因为放宽
就把真耦合也吞掉**）。

### 3.34 `GOPRIVATE` 把 `GOPROXY=off` 架空了 —— 审计在联网上挂几个小时

**现象**：审计一个 Go 仓，20 个提交跑了几小时还没完。进程停在
`git fetch ... https://github.com/aws/aws-sdk-go-v2` 和一串
`git ls-remote` 上 —— **在联网拉模块**，而这个环境到 GitHub 的速度是
68 KB/s 且经常直接连不上。

**根因**：`GOPRIVATE=github.com/*/*`（脚本为了能拉私有仓设的）会**连带把
`GONOPROXY` 设成同样的模式**。`GONOPROXY` 里的模块**绕过 `GOPROXY`** ——
包括绕过 `GOPROXY=off`。于是那句「离线」是**形同虚设**的：go 认为这些
模块该直连，就直连去了。

这不是配置失误，是 Go 的机制：**`GOPRIVATE` 不只管私有性，它同时改写了
代理策略**。想离线，得把 `GONOPROXY` 单独钉死。

**修复**：审计阶段显式写 `GONOPROXY=none`，`GOPROXY=off` 才有约束力。
缺依赖时 go 立刻报「module lookup disabled by GOPROXY=off」（**快、响、
可判**），而不是挂在连接上等几小时。

**配套**：验收脚本加了**依赖预热**步骤 —— 克隆之后先用网络把依赖灌进本地
模块缓存，之后审计全程离线。预热一次，之后几十次审计都是本地速度。

### 3.35 两个验收脚本同时跑，把彼此正在下载的克隆目录删了

**现象**：验收跑到一半，`results.tsv` 里的行数**倒退**了（9 行变 3 行）；
两个 `git clone` 进程卡在同一个目录上，40 分钟一个字节没多。

**根因**：验收脚本用的是**固定的**工作目录（`/tmp/vacuous-accept/<仓名>`），
而且克隆前会 `rm -rf` 一次。后一个进程 `rm -rf` 的时刻，前一个正在往那个
目录里下载 —— 目录被删掉，前一个进程接着往**已经被 unlink 的 inode** 里写。
两个进程都拿不到完整克隆，而且**没有任何一个会报错**：它们只是在安静地
写进一个没人引用的文件。

**后果**：不只是白费带宽。更坏的情况是**验收结果本身不可信** —— 第二个
进程把第一个进程的结果行覆盖掉，看起来像「跑过了」，其实那批数据来自一个
被中途删掉的检出。

**修复**：① 脚本加**锁**（`mkdir` 原子锁，带 stale 判定），两个验收不并发；
② 克隆目录**存在就复用**（网络差的时候重新拉一遍是最贵的一步）；
③ 克隆阶段和审计阶段**分开**，审计阶段只读本地、不联网；
④ 验收表**追加**而不是覆盖。

**顺带修的两个自伤**：
- 并行克隆的等待策略原来是「等最老的那个 job」—— 一个 300MB 的大仓能把
  整条队列堵住，剩下的小仓干看着排队。改成「等任意一个结束」。
  macOS 的 bash 是 3.2，没有 `wait -n`；而 `jobs -pr` 在**命令替换的子
  shell 里永远是空的**，用了它就退化回「等最老的那个」—— 判活只能用
  `kill -0`。
- bash 在 UTF-8 locale 下会把紧跟变量名的中文字符**并进变量名**
  （`$VAR（` 会被解析成变量 `VAR（`）。验收脚本扫过一遍，0 处。

### 3.36 「每个提交都有交代」不等于「验出了东西」

**现象**：三个仓的验收结果全是 PASS，但报告里 `proven: 0`、`vacuous: 0` ——
**每一条判定都是 environment**。

**根因**：验收脚本原来只核对三件事：跑完了、每个提交都有交代、只读。
「每个提交都有交代」这个条件，**20 个提交全是 environment 也照样满足**。

**后果**：这三条标准量的是**脚本**，不是**工具**。一份「PASS」说明脚本没崩、
计数对得上、仓库没被改 —— 但它一点也不能说明工具**能判断测试到底看没看
守着修复**。而工具的核心能力恰恰是那个 `proven` / `vacuous`。

**修复**：验收表加两列 —— **结论数**（proven + vacuous + no_test，即真的
下了结论的提交数）和**严格判定**（proven + vacuous，即最能说明问题的那
两个）。跑完了但结论数为 0 的仓，结果写成 `PASS_NO_CONCLUSION`，
**不混进 PASS**。

这三个仓最后查出来是同一个原因：**依赖没在本地模块缓存里**，于是每个提交
都落成 environment（3.33、3.34）。补上预热之后，同一批提交判出了
**3 个 proven**。

### 3.37 「没有测试运行器」这句话，把两种情况说成了一种

**现象**：验收 14 个仓，有 5 个仓的审计报「no supported test runner found」。
其中一个仓的**静态体检**却报出了 **9 条 skipped-test**，全部指向
`workbench/tests/voc_tests/*.py` —— **同一个仓，同一次运行，体检说有 Python
测试，审计说没有测试运行器。**

**根因**：Python 适配器只驱动 **pytest**。那个仓用的是
`python -m unittest discover`（标准库自带的，CI 里就是这么跑的）。
而体检的静态分析不关心用什么跑，它只找测试文件 —— 于是两边看的是同一个仓，
得出的却是相反的结论。

**后果**：这句话会把读者带偏。「这个仓有测试，但工具跑不了」和「这个仓压根
没有测试」该做的下一步完全相反：前者该去加适配器，后者该去写测试。
说成后者，读者就不写了。

**修复**：找不到适配器时，先扫一遍仓里有没有**工具跑不了的 Python 测试套件**
（按目录找 `test_*.py`，并排除 pytest 项目的子树 —— 判据要看**整条祖先链**，
因为 pytest 配置常常在仓根而测试在子目录）。有就把话说准：

> 这个仓的 Python 测试用的是 python -m unittest（7 个目录），这个工具现在只会
> 驱动 pytest，跑不了它们；先用 --mode check 看静态体检的结果

真没有测试的仓（比如一个 646MB 的研究语料仓）仍然是原来那句话。

**负对照**：① pytest 项目（有 `pyproject.toml`）**不能**被认成 unittest 项目 ——
把祖先链的判定拿掉，测试立刻变红；② 没有测试的仓**不能**被说成 unittest 项目。

**这个缺口没被填上**：工具**仍然跑不了** unittest 的仓。加一个 unittest 适配器
（多目录 discover + 解析 unittest 的输出 + 把用例映射回文件）是一件事，
不是顺手能做的。没做就说没做。

### 3.38 Node 仓没装依赖，套件起不来

**现象**：一个 Node 仓的 8 个提交全判成 `suite-crash`（「测试套件没有跑起来
—— 它一个用例都没执行，所以什么都没证明」）。

**根因**：克隆里没有 `node_modules`。工具的 Node 适配器会把调用方的
`node_modules` 复制进反事实检出 —— 源目录里没有，复制过去自然也没有。
vitest 找不到，套件起不来。

**后果**：判得没错（套件确实没跑起来），但**什么结论都得不到**。跟
environment 一个毛病：诚实，但是空的。

**修复**：验收脚本在克隆之后装依赖（认 lockfile 类型：`package-lock.json` →
`npm ci`，`pnpm-lock.yaml` → `pnpm install --frozen-lockfile`，
`yarn.lock` → `yarn install --frozen-lockfile`，都没有 → `npm install`）。
装上之后，同一个仓的同一个窗口判出了 **6 个 proven**。

**顺带**：这 6 个 proven 是**全量套件回退**带来的。窄跑（只跑这次改动涉及的
测试文件）全绿，回退到全量套件才看见红灯 —— 那个看守修复的测试住在别的目录。
这正是修 issue #5 要治的假阴性。

### 3.39 仓自带一套验证命令，工具却说它「一个测试文件都没有」

**现象**：一个 Node 仓被报成高危：

> **[HIGH] no-test-for-fix** 这个仓库有代码，但一个测试文件都没有
> 仓库里有 25 个源文件，但没有找到任何测试文件，也没有能跑测试的命令。
> 这意味着这里的每一次行为修改都没有对应的断言 —— 改错了，没有任何东西会变红。

退出码 1。而那个仓有 **13 个验证脚本**（`scripts/verify/*.mjs`），外加一个
CSS 冒烟脚本，靠 `npm run verify` 跑（AGENTS.md 把它记成这个仓的验证入口：
「build + 起 preview + 跑全部 + 汇总，失败即非零退出」）。**它有检查，而且
有 13 个。**

（顺带记一笔：那个仓**没有 CI** —— 没有 `.github/`，没有 yml。所以这套脚本
目前是**手动跑**的，AGENTS.md 里也留着「该把它接进 CI」这件事。**这跟工具
的误报是两回事**：工具判「一个测试文件都没有」仍然是错的，但「检查没被自动
执行」这件事确实成立，只是**不是这个工具该报的**。）

**根因**：`noRunnerFinding` 判断「这个仓有没有测试」，靠的是
`testCount` —— 按**四种文件名形状**数：`*_test.go`、`test_*.py`、
`*.test.*` / `*.spec.*`、以及 `test/` `tests/` `__tests__/` 目录下的文件。
`scripts/verify/run-all.mjs` **四种都不匹配**。而「有没有能跑测试的命令」
这件事，工具**根本没看** —— 它只看 package.json 里有没有叫 `test` 的
script。`verify` 不叫 `test`，于是整条线索被漏掉了。

**后果**：这是**误伤**，而且是最伤人的那种误伤。读者被告知「你一个测试都
没有，去写」，而他要去写的东西**仓里已经有了**，连形式都一样（都是
`npm run` 跑脚本）。工具还说得很有把握：给了源文件数、给了「找到的测试
文件数: 0」。**一个总是误报的闸门，最后是被 --no-verify 关掉的。**

**修复**：先问「这个仓自己怎么跑检查」，再下结论。新增
`detect.HarnessCommands` —— 从 `package.json` 的 scripts 里找**名字像检查**
（test / verify / check / smoke / e2e / unit / spec / validate）**且命令跑
本仓里一个脚本文件**的 script。找到就不报 HIGH，改报 INFO：

> [INFO] unsupported-tests 这个仓有自己的验证命令，但这个工具跑不了它们
> 仓库里有 25 个源文件、0 个工具能识别的测试文件，但找到了 2 个这个工具
> 跑不了的验证命令：
>   npm run smoke:css → node scripts/smoke-test-css.mjs
>   npm run verify → node scripts/verify/run-all.mjs
> 所以这份报告没有覆盖到这些检查 —— 不是这个仓没有检查，是我没看。

那个仓的退出码从 1 变成 0。**它本来就不该让闸门变红** —— 有检查的仓不是
缺陷的仓。

**负对照**：判定由 6 条规则合起来，每一条都被**单独拆掉验过**（拆完跑测试，
必须变红）：

| 拆掉的规则 | 变红的测试 |
| --- | --- |
| 整个探测（永远返回空） | 6 条 |
| 脚本名过滤（任何 script 都算检查） | 2 条 |
| 「工具能驱动的 runner 不算盲区」 | 2 条 |
| 扩展名过滤（`.json` 不算脚本） | 1 条 |
| 跨仓路径检查（`../` 指向别的仓） | 2 条 |
| 目录不是脚本 | 1 条 |

第一版里有两个**假负对照**：跨仓那条和「工具能驱动的 runner」那条，
**拆掉规则后测试照样全绿** —— 因为夹具里的那个脚本在磁盘上根本不存在，
文件先被「不存在」这条规则筛掉了，压根没走到被测的那条规则上。改成
**兄弟仓的脚本真的建出来**、命令里**真的带一个本仓文件**之后，两条才
各自有了牙齿。**负对照绿着不红，多半是它压根没测到那件事。**

**这个缺口没被填上**：工具**仍然跑不了**这种验证命令 —— 它只认
jest / vitest。要审 `npm run verify` 这种套件，得加一个能驱动任意命令的
适配器（跑它、拆它的退出码、认出哪条断言红了）。没做就说没做。
另外，**这个仓自己也没有被审**（本条只解决了「别误伤」，没解决「审它」）。

### 3.40 检查脚本没登记在 package.json 里，工具报「一个检查都没有」

**现象**：仓库 F（一个库仓）被报成高危 `no-test-for-fix`：
「仓库里有 3 个源文件，但没有找到任何测试文件，也没有能跑测试的命令」，
外加一句「改错了，没有任何东西会变红」，退出码 1。

**根因**：`HarnessCommands`（3.39 建的）只读 `package.json` 的 `scripts` 段。
而这个仓的检查脚本**不在它自己的 package.json 里** —— 因为**调用它的是消费方**：

```json
// 消费方（仓库 E）的 package.json
"check:theme": "node ../theme-pkg/scripts/check-consumer.mjs src/styles"
```

于是这个检查**两边都看不见**：消费方那一侧，工具**故意**不认这条命令
（`harnessLocalFiles` 跳过 `../` 开头的路径 —— 那是兄弟仓的 harness，
不是这个仓的）；库那一侧，它自己的 package.json **连 scripts 段都没有**。

上一轮的人工核实也写「它确实一个检查都没有」—— **人工核实自己漏了**，
犯的正是 3.39 里记的同一个毛病：只查了「文件名像不像测试」和「package.json
里有没有登记」。而且这个检查**不是躺在仓里没人跑**：消费方的 `npm run build`
每次都跑它（`build` → `check:theme` → `check-consumer.mjs`）。

**后果**：高危 + 退出码 1。读者被告知「改错了，没有任何东西会变红」，
而实际上有东西会红 —— 在消费方那边。这是 3.39 那个误伤的**一层更深版本**。

**修复**：新增 `detect.LocalCheckScripts` —— 在仓库自己的 `scripts/`、
`bin/`、`tools/` 里找**文件名说「这是检查」**的脚本。工具仍然跑不了它们，
但报告里要点名，读者才知道「这个仓有检查，是我没看」。

规则刻意窄：

- 关键词后面必须跟分隔符（`-` `_` `.`），所以 `checkout.py`、
  `checkstyle.mjs` 不算
- `test` **不在**关键词表里 —— 叫 `test-xxx` 的是测试文件，工具对那种
  已经有话说（「有测试但没人跑」），在这儿把它算成「有检查」会把那条警告盖掉
- 只在 `scripts/` `bin/` `tools/` 三个目录里找；`src/` 下的同名文件是
  产品代码，不是谁会运行的命令
- `package.json` 已经登记过的文件不重复计数
- **只在一个测试文件都没有的时候才补充** —— 仓里有测试文件时，
  「有测试但没人跑」那条警告比这个更有用

**负对照**：6 条，逐条验证过「把规则改坏，测试必须变红」：

| 改坏的地方 | 变红的测试 |
|---|---|
| 关键词匹配恒为 false | `FindsAnUnregisteredCheckScript` 等 3 条 |
| 目录规则只认 `scripts/` | `FindsChecksInTheOtherToolingDirectories` |
| 扩展名规则放行一切 | `IgnoresAWordThatMerelyStartsLikeAKeyword` |
| 去重规则失效 | `IgnoresAScriptPackageJSONAlreadyNames` |
| 运行器映射写错（python 当 node） | `FindsACheckInAnotherLanguage` 等 2 条 |
| CLI 不再调用 `LocalCheckScripts` | `DoesNotCallALibraryPackageUnprotected` 等 2 条 |

> **第一版这里有 1 条假负对照，是复核时抓出来的**：目录规则改成「只认
> `scripts/`」之后，测试**照样全绿** —— 因为当时没有任何一条用例用到
> `bin/` 或 `tools/`。规则没被测到，负对照就抓不到它。补了
> `FindsChecksInTheOtherToolingDirectories` 之后，改坏才变红。
> **负对照绿着不红，多半是它压根没测到那件事** —— 这条已经在这个仓里
> 栽过两次了（见 3.39 和 4.1）。

**修完之后**：仓库 F 报 `unsupported-tests`（信息级），并把命令点名列出来：

```
  [    INFO] unsupported-tests    (仓库根)
      这个仓有自己的验证命令，但这个工具跑不了它们
      说明: 仓库里有 3 个源文件、0 个工具能识别的测试文件，但找到了 1
      个这个工具跑不了的验证命令：
        node scripts/check-consumer.mjs
```

注意它**没有丢掉**「0 个工具能识别的测试文件」这个事实 —— 那句话还在，
读者仍然知道这个仓没有它能驱动的测试；而「守住了什么」交给读者自己用
反事实的办法验。**误伤去掉是真的信号**（工具以前说「一个检查都没有」），
**真信号没丢**（工具现在说的是「有检查，但我跑不了」）。

其余 5 个仓**逐条不变** —— 这个规则只在「一个测试文件都没有」的仓上生效，
而 仓库 A / B / C / D 都是 Go 仓（有 runner，压根不走这条路径），
仓库 E 早就被 3.39 修成信息级了。

### 3.41 反事实实验没有基线对照 —— 「本来就在的红灯」被说成「测试在看守修复」

**现象**：在一个超大型公开仓上跑审计，一个提交被判成 **vacuous（空洞测试，
严重级）**：「这个测试在撤掉修复后依然是绿的 —— 它没有测到修复修的那个行为」。

**根因**：反事实实验问的是「**撤掉修复后有没有东西红**」。它回答不了
「**是不是撤掉修复让它红的**」。

反事实树是「父提交 + 测试侧补丁」。如果那个仓的测试套件**本来就是红的**
（或者有一个 flaky 的测试），那个红灯在反事实树里也会亮 —— 而它和这次修复
一点关系都没有。工具会把这样一个红灯写成「测试在看守修复」。

**人工核实的过程**：报告里写着「3439 通过 · 0 失败」。我按工具自己给的配方
手工复现（父提交的树 + 只打测试补丁），却拿到「3420 通过 · **19 失败**」。
两边对不上，于是逐层查：

1. 抓工具自己的工作树，比对文件哈希 —— **树是对的**（`meta.go` 是父提交版本，
   测试文件是提交版本，修复确实留在外面）；
2. 把工具这次运行的原始输出抓下来自己数 —— **确实是 0 失败**；
3. 把工具自己的解析器喂真实事件流 —— **解析器是对的**；
4. 最后发现：那几个 fmt 测试**在并行跑的时候是飘的**。同一棵代码树，
   一次红一次绿，取决于机器当时的负载和调度顺序。

**后果**：工具的判定会跟着飘。同一个提交，一次是「空洞测试」（严重级，
读者会删测试），一次是「proven」。

**修复**：反事实树红了的时候，**再跑一遍基线** —— 带着同一个修复的同一个提交，
同一个测试范围。

比的是**哪些测试**，不是**几个失败**：

- 基线里**不红**、反事实里**红**的那些测试 = 撤掉修复弄红的那些 = **看守**
- 空的（反事实里的红，基线里全都有） → 那些红灯本来就在 → 新判定
  **`pre-existing-failure`**，不下结论
- 基线**跑不起来** → 同样不下结论（基线没回答问题，就不能拿它当依据）

**比集合而不是比数量，这一条是被真实仓教会的**：example-main 的一个提交，反事实红
2 个（一个是既存的红灯，一个是真正看守修复的测试），基线红 1 个。数量差 1 →
判定说「有新的东西」→ proven —— **但哪个是新的并没有问**。改成集合差之后，
看守被认出来，既存的红灯被认出来，两个都对。

更极端的形状也要对：反事实红 {A,B}、基线红 {A,C} —— **数量相同，集合不同**。
数量比较会说「没变化」，把看守丢掉；集合比较说「B 是新的」，守住了。

三种形状各有夹具钉着：既存红灯没带来新红灯 → `pre-existing-failure`；
既存红灯 + 真看守 → **proven**（看守不能被既存的红灯淹掉）；数量相同但集合
不同 → **proven**。

**顺带修了一个真 bug**：基线检出之前**没有做**反事实检出那套准备
（`PrepareWorktree` 会在检出里生成一个 `generated` 包，替掉没入库的构建产物）。
少了这一步，基线建不起来 → 所有红灯都被当成「本来就在」→ **真看守全被丢掉**，
而且报告里看不出为什么。

那个提交因此从「空洞测试」变成 **proven** —— 而后者是**对的**：那个提交确实
修好了 fmt 测试（旧版的 `meta.go` 会让它们红），工具原来的「空洞」判定是
一次 flaky 竞争造成的假阴性。

**为什么这是本工具能犯的最贵的错**：报告上写「测试在看守修复」，读者读到之后
的下一个动作是**删掉一个本来没问题的测试**。这比误报严重 —— 误报只是让人忽略
一条消息，误伤会让代码库少一个守卫。

**负对照**：把基线那一段判空（`countFailures(result) > 0 && false`），
`TestAuditDoesNotClaimAProofFromAPreExistingRed` 立刻变红；改回来，绿。
另外 `TestAuditProvesRealTest` 钉住了另一头：**基线是绿的**时候，原来的
proven 判定一点没变。

「基线检出没做那套准备」这一条另有负对照：`TestAuditComparesLikeWithLike`
（夹具 `GeneratedInputFixture`）—— 那个仓的包 `//go:embed` 了一个 git 不跟踪的
文件，**反事实树**因为拷贝了未入库的构建产物能编译，**基线树**（提交自己）
不能。少了那步准备，基线建不起来 → 判决从 **proven** 掉成
**pre-existing-failure**（真看守被当成「本来就在的红灯」丢掉了）。

### 3.42 工具不会驱动 `python -m unittest` 的仓

**现象**：两个仓的审计报「这个仓的 Python 测试用的是 `python -m unittest`，
这个工具现在只会驱动 pytest，跑不了它们」。

**根因**：Python 适配器是 pytest 专用的。而真实仓里用标准库 unittest 的不少 ——
CI 里就是 `python -m unittest discover -s workbench/tests -p 'test_*.py'`。

**后果不是「少审两个仓」**：同一个仓的**静态体检**明明能找到那些 Python 测试
（还报出了 9 条 skipped），而**审计**说没有测试运行器。**同一个工具，
同一个仓，两边说法相反。**

**修复**：工具能驱动 unittest 了。三处容易错的地方：

1. **`-s`（从哪开始发现）和 `-t`（模块名相对于谁）决定 import 能不能成功。**
   拿叶子目录当 `-s`，16 个用例**全部 import 失败**（实测）。发现根的规则：
   目录不是 package 就用它自己；是 package 且父目录也是 package 就用父目录
   （模块名 `voc_tests.test_x`，与 CI 的 `-s workbench/tests` 等价）。
2. **unittest 没有 JUnit XML**，只有 stderr 上的文本，格式还随 Python 版本变
   （≤3.10 是 `name (module.Class)`，3.11+ 是 `name (module.Class.method)`；
   有 docstring 时状态单独一行）。解析只认 ok/FAIL/ERROR/skipped 四种，
   **认不出来就不记**；结尾的 `FAILED (failures=N, errors=M)` 与逐行统计
   **交叉核对**，对不上就判「解析不可信」（fail closed）。模块 import 失败算
   **suite crash**，不是「测试变红」。
3. **退出码语义和 pytest 不同**：unittest 的 >1 是用法/内部错误，不能当成
   「一个测试失败了」。

**真实仓验证**：两个仓从「跑不了」变成真判定（各 1 个 proven，其中一个手工
复现过反事实树 —— 提交自己新加的测试在撤掉修复后确实变红）。第三个仓的
workbench 套件因为本机 Python 3.9 而那个仓 CI 钉的是 3.12，报 suite-crash ——
**环境问题，如实不下结论**。

**负对照**：9 条，全部实测（改坏 → 对应测试变红 → 改回，源文件逐字节一致）。

### 3.43 基线跑不起来，被说成「这个红灯本来就在」

**现象**：一个提交被判成 `pre-existing-failure`。报告的 Summary 写着「这个提交
没法判定：这个红灯本来就在，不是撤掉这次修复造成的」，Hint 写着「这通常意味着
两件事之一：这个仓的测试套件本来就是红的（或者有 flaky 的测试）……先把套件弄绿，
再回来审」。

**根因**：基线对照要回答的问题是「**这个红灯是不是本来就在**」。基线**没跑起来**
的时候，这个问题**没有人回答过** —— 但代码把「基线跑不起来」和「基线跑起来了
而且是红的」归成了同一件事，两种都写成 `pre-existing-failure`。

**后果**：报告把**套件是绿的**说成了**套件本来就是红的**，并且让读者去修一套没坏
的测试。坏掉的是**检出**（少了构建需要的东西），不是测试。这跟 3.41 想防的
是同一类错 —— 把工具没看过的东西说成看过了 —— 只是方向相反：**3.41 是把红的
说成绿的（ accuse 一个没看过的测试），3.43 是把绿的说成红的（让读者去修一套绿
的测试）**。

**人工核实**：用一个夹具复现 —— 提交自己嵌了一个 git 不跟踪、工具也不拷贝的
文件（`meta/version.txt`）。于是：

- **父提交**能编译；
- **反事实树**（父提交 + 测试补丁）能跑，而且是红的 —— 看守失败（这正是应该的）；
- **基线**（提交自己）编译不过：`pattern meta/version.txt: no matching files found`。

工具的输出里，「基线编译不过」出现在 Detail 里，但 Summary 和 Hint 说的是另外
一回事 —— Detail 诚实，另外两句在替工具**没验证过的**结论背书。

**修复**：基线跑不起来，和基线是红的，分开。`baselineOutcome` 记三件事：看守
集合、基线跑没跑、说明。

| 基线 | 判决 |
|---|---|
| 跑了、看守集合是空的 | `pre-existing-failure`（真的本来就在） |
| 跑了、有看守 | **proven** |
| **没跑** | **environment**（检出缺东西） |

基线没跑的时候，报告说的是「**没有人回答过**」，并且明确写一句「套件本身可能是
绿的 —— 坏的是检出，不是测试」，不再替套件认罪。

**负对照**：把 `baselineUnknown` 那一条改回 `VerdictPreExistingFailure`，
`TestABaselineThatCouldNotRunIsNotAPreExistingRed` 立刻变红 —— 判决变回
pre-existing-failure，Summary 又开始说「这个红灯本来就在」；改回来，绿。

### 3.44 工具说自己「只会驱动 pytest」—— unittest 适配器落地之后这句话没跟着改

**现象**：审计报告里写着「这个工具只会驱动 go test / pytest / jest / vitest，
跑不了它们」，和「这个工具目前只会跑 Go、Python（pytest）和 Node（jest/vitest）
的测试」。

**根因**：unittest 适配器（3.42）落地之后，这几处**硬编码**的句子没有跟着改。
清单写在三个地方，适配器加了一个，三处都还在。

**后果**：这是**关于覆盖率的谎话**。报告的这句话是「我看不到这一部分」的承诺，
读者靠它决定还要不要自己看。一个用 unittest 的仓读了这句话 → 以为工具没审过
自己的测试 → 不看了。而工具其实跑了，而且有判决。

**说自己看不到，比说错更糟**：说错，读者自己跑一遍就能发现；说自己看不到，
读者就**不跑了**。

**修复**：清单只有一份（`adapters.SupportedRunners`），所有提到「工具能驱动什么」
的句子都由它生成。新适配器不来登记，报告就会跟真实能力脱节 —— 这个错由测试
钉住，不靠自觉。

**负对照**（两条都实测）：

1. 把 `python -m unittest` 从清单里删掉 → `TestTheToolCanDriveEveryRunnerItClaims`
   立刻变红（工具明明能驱动 unittest，清单却不承认），detect 和 cli 两处
   `…NamesUnittest` 也变红。
2. 把句子改回硬编码 → detect 和 cli 两处 `…NamesEveryClaimedRunner` 立刻变红
   （句子漏掉了清单里的运行器）。

### 3.45 夹具（testdata）被当成测试 —— 报告说「覆盖率会算进去」，可它从来就没被算过

**现象**：工具审自己（`--mode check .`）报 26 条，其中 3 条指向
`internal/adapters/testdata/` 底下的**夹具文件**：

| 文件 | 夹具里的那句 |
|---|---|
| `internal/adapters/testdata/goproj/add_test.go:15` | `t.Skip("not ready yet")` |
| `internal/adapters/testdata/nodeproj/sum.test.js:7` | `test.skip('is pending', …)` |
| `internal/adapters/testdata/pyproj/test_calc.py:13` | `pytest.skip("not ready yet")` |

这三份文件是**别的仓的样本** —— 它们是给适配器当输入用的夹具，不是这个仓的测试。

**根因**：`testdata` 是「测试要用的数据」的约定，**不是测试代码**。Go 工具链
**直接无视**它：testdata 底下的 `_test.go` 永远不会被编译、不会被跑，也**不会被
覆盖率算进去**。

而适配器那层**早就知道**这件事 —— `adapters.skipPackageDir` 明确把 testdata
排除在 Go package 之外。**静态检查那层不知道** —— `detect.isTestPath` 只看文件名，
`add_test.go` 就是测试文件。

同一个目录，两处给出相反的判断。这和 3.44 是同一个病根：判断写在两处，其中一处
没跟上。

**后果**：报告写的是「被跳过的测试没有证明任何事 —— **覆盖率会把它算进去**，但它
一次都没跑过」。这句话落在 testdata 上，**每一句都是错的**：它不是测试，覆盖率也
从不数它。读者收到的是一条指控，指控对象是一份夹具。

**修复**：`detect.isTestPath` 加一条 —— 路径里有一段叫 `testdata` 的，就不是测试
文件。名字**精确匹配**：`testdata2`、`testutils` 是普通代码，照样要扫。

**负对照**（两个方向各有自己的用例，拆哪一半都会红）：

| 拆掉的修复 | 变红的用例 | 保持绿 |
|---|---|---|
| 整条 testdata 规则去掉 | `TestTestdataIsNotTestCode`（4 个夹具全被报成「跳过测试」）、`TestTestdataFilesAreNotCountedAsTests`（夹具被当成 2 个测试文件） | `TestOnlyAnExactTestdataDirectoryIsExcluded` |
| 精确匹配改成前缀匹配 | `TestOnlyAnExactTestdataDirectoryIsExcluded`（`testdata2/` 里的真测试被漏掉） | 上面那两条 |

变红时报出来的正是生产症状：

```
--- FAIL: TestTestdataIsNotTestCode
    a fixture under testdata is not a test and must not be reported as a
    skipped test: testdata/fixture_test.go
```

**现场验证**（真仓，不是夹具）：

- 工具审自己：**26 条 → 23 条**。消失的正好是那 3 条夹具；23 条真跳过
  （`t.Skip("skipping: runs a real go test")` 之类）一条没少。
- 6 个被审仓**逐条比对**（`--mode check --json`，改前 / 改后）：仓库 B 3 条、
  仓库 I 1 条、仓库 C 7 条、仓库 D 1 条、仓库 E 1 条、仓库 F 1 条
  —— **全部一模一样**。修掉的是夹具，没碰到任何真信号。

**记一笔（当时还没修，2026-10-21 晚的那一轮修掉了 —— 见 3.51）**：同一个
「testdata 不是代码」的判断，**还有一处**不知道。

> **这一条当初指错了地方，这里更正。** 原来写的是
> `internal/git/istest.go` 的 `isTestPath`「审计侧用它判断改动的文件是不是
> 测试」。**不是的**：那个函数写出来的 `core.FileChange.IsTest` 字段
> **在 `internal/git` 包外从来没有被读过**（`grep -rn IsTest` 只命中
> `core/git.go`、`git/git.go`、`git/git_test.go`）。判决真正的来源是
> `internal/counterfactual/audit.go` → 适配器的 `IsTestPath` / `IsSourcePath`。
>
> **按原来的指路去改，改了也不会改变任何判决** —— 那一轮就是这样白找了一趟。
> 教训有两条：**死代码不能当指路牌**（它写得像那么回事，但没人读它）；
> **指路必须指到「读取它的地方」，不是「写它的地方」**。

改动影响和别处不一样，所以当时没有顺手改：它动的是判决。

> 同一份清单里的另外两处（Python 适配器的套件发现）后来修掉了，见 3.50 ——
> 那条不是「同一个判断的另一处」那么简单：执行层跑夹具会**崩**，然后把夹具的
> 锅扣到真测试头上。

### 3.46 仓库根目录的 unittest 套件，工具根本看不见

**现象**：一个把测试放在仓库根目录的项目（`test_thing.py` 和代码并排），
工具说 `no supported test runner found`，退出码 2；`--mode check` 则报
「仓库里有测试文件，但没有能跑它们的命令」（警告级）。

**根因**：`UnittestSuites` 遍历目录时遇到**仓库根目录**就直接跳过
（`if rel == "." { return nil }`）。根目录被跳过了 → 根目录里的测试文件
不算一个套件 → 适配器不接管这个仓 → 工具说自己跑不了。

这段跳过是 `b4fa616` 留下的，**比 unittest 适配器（3.42）还早** —— 当时
「根目录」确实没有意义，后来它有了：**根目录里的测试文件是平铺的模块**，
`python -m unittest` 点名就能跑。

**后果**：**漏报**。工具对一个测试跑得好好的仓说「没有能跑的运行器」，
读者要么去装一个不需要的东西，要么以为这个仓没测试。同一套测试往下挪
一层就能被认出来 —— 这正是「工具的毛病出在遍历的细节上」的样本。

**修复**：根目录也算一个套件，用 `"."` 表示。根目录里的测试文件按**模块名**
一个一个点名跑（原因见 3.47）。

**负对照**（实测）：把 `rel == "."` 的跳过放回去 →
`TestUnittestSuitesFindsTheRootSuite` 立刻变红。

### 3.47 从根目录跑套件，会把底下的包一起拖进来 —— 误伤

**现象**：根目录有 `test_root.py`；`sub/` 是一个包（有 `sub/__init__.py`）；
`sub/test_sub.py` 里写的是 `from helper import VALUE`，而 `helper.py` 在
`sub/` 里。工具跑根目录的测试 → 报
`ModuleNotFoundError: No module named 'helper'` → 套件崩了 → 判决
「这个套件没有跑起来」。

**根因**：`unittest discover -s .` **会走进起点下面的包目录**（实测：只递归
进含 `__init__.py` 的目录）。于是根套件把 `sub` 的测试也收进来了 ——
而 `sub` 本身就是一个套件，工具也会单独跑它。两件事叠在一起：

1. 同一个测试跑了两遍；
2. **import 路径变了**。`from helper import ...` 只有在 `sub/` 自己挂在
   import 路径上时才成立 —— 那是项目跑它的方式。从根目录跑，挂在路径上的
   是仓库根，于是 import 失败。

**后果**：**误伤**。一个健康的仓，工具报它「测试套件没跑起来」，还附一条
「先修 import」的提示 —— 而 import 根本没坏。读者去改一个没坏的测试。

**修复**：根套件不用 discovery，改为**按模块名点名**跑根目录自己的文件
（`python3 -m unittest -v test_root`）。底下的包交给拥有它们的套件去跑。

子目录的套件仍然用 discovery —— 那里 import 路径和项目一致，discovery 是
对的。代价是「套件里套着包」时那个测试仍会跑两遍：**判决不受影响**（同一个
测试状态一样），但**计数**会多。合并结果时按测试名去重，且**红灯优先**
（同一个测试两副面孔时，失败的那副算数）。

**负对照**（实测）：

| 改坏的地方 | 变红的用例 |
|---|---|
| 根套件改回 `discover -s .` | `TestTheRootSuiteRunsOnlyItsOwnTestFiles`、`TestTheRootSuiteDoesNotDragInThePackagesBelowIt`、`TestARunOfARootLevelSuiteDragsInNothing` |
| 运行层绕开 `unittestRuns`（接线断开） | `TestARunOfARootLevelSuiteDragsInNothing`、`TestARunCountsATestOnce` |
| 合并时不去重 | `TestARunCountsATestOnce` |
| 根套件不再「处处都在」 | `TestTheRootSuiteIsNearEveryChange` |

> 最后一条是复核时才发现的洞：`unittestSuiteNear` 里「根套件离任何改动都近」
> 这条规则**一条负对照都没有**。它坏了不会让任何测试变红 —— 而它坏了的
> 后果是「根目录的测试不再跑」，工具会把一个**真的在看守修复**的测试判成
> 「空洞」。

### 3.48 `thing_test.py` 这种命名的测试文件，工具「数得出来、跑不起来」

**现象**：一个只有 `foo_test.py` 的仓 → 适配器接管了，但 discover 的
pattern 是 `test_*.py` → 一个文件都没收集到 → 报告说
「测试套件没有跑起来 —— 它一个用例都没执行」，并附一条「先修 import」的提示。

**根因**：**两份**「什么算 Python 测试文件」的判断：

| 地方 | 认 `test_*.py` | 认 `*_test.py` |
|---|---|---|
| `dirHoldsPythonTests`（套件发现） | ✅ | ✅ |
| `testCount`（静态体检） | ✅ | ✅ |
| discover 的 `-p` pattern | ✅ | ❌ |

计数器说「这个仓有测试」，跑的去只认另一种命名。

**后果**：**漏报**（方向是安全的那个）。工具不下结论，但它把读者送去修一个
没坏的 import。根目录这一条还更糟一点：工具接管了这个仓，`--mode check`
于是**什么都不说** ——「有测试但没人跑」这条警告被消掉了。

**修复**：pattern 按目录里实际存在的命名选；两种都有就**跑两遍**，一遍一种
（少哪一种，那个命名的测试文件就一次都没跑过 —— 一次都没跑过的测试，什么
都看守不了）。

**负对照**（实测）：

| 改坏的地方 | 变红的用例 |
|---|---|
| pattern 硬编码回 `test_*.py` | `TestThePatternCoversTheSuffixConvention`、`TestASuffixNamedTestFileIsActuallyRun` |
| 混合目录只跑一种命名 | `TestThePatternCoversBothConventions`、`TestASuiteWithBothConventionsRunsTwice` |

### 3.49 运行器清单可以静默缩水 —— 复核发现的假负对照

**现象**：把 `adapters.SupportedRunners` 里的 `"go test"` 和 `"jest"` 删掉 →
**全部测试仍然全绿**。

**根因**：`internal/adapters/runners_test.go` 里的每一条测试都是**拿清单
和它自己比**（自指）。`TestTheToolClaimsNoRunnerItCannotDrive` 检查的是
「清单里没有工具驱动不了的运行器」—— 这拦得住**多**，拦不住**少**。

**后果**：清单是「工具能驱动什么」的唯一出处，3.44 之后所有提到覆盖率的
句子都由它生成。清单悄悄少一项 → 报告开始说「你的一部分测试我没覆盖」
—— 而工具明明能覆盖。**谎话的方向是「说自己看不到」**，比说错更糟：
说自己看不到，读者就不自己跑了。

**修复**：补一条「清单必须恰好是这五项」的用例。

**负对照**（实测）：删掉 `"go test"` 和 `"jest"` →
`TestTheClaimedRunnersAreExactlyTheOnesTheToolDrives` 立刻变红。

> 这条和 3.44 是同一个病根的另一半：3.44 修的是「句子和清单脱节」，
> 这条修的是「清单自己会跑」。

### 3.50 Python 适配器的套件发现不认识 testdata —— 夹具的锅扣到真测试头上

**现象**：一个 Python 仓，根目录有真测试 `test_calc.py`，另有一个
`testdata/` 目录放着别家仓的样本。工具审它，报的是：

```
[WARN] suite-crash   test_calc.py
    测试套件没有跑起来 —— 它一个用例都没执行，所以什么都没证明
    证据: 命令: python3 -m unittest -v test_calc && python3 -m unittest discover -v -s testdata -t testdata -p *_test.py
          testdata/sample_test.py: the test module could not be imported: ModuleNotFoundError: No module named 'fixtures'
    怎么修: 先让这个测试文件自己能跑起来（修 import、把 beforeAll 里的副作用挪走），再审这个提交
```

**根因**：`UnittestSuites` 遍历目录时跳过的清单里没有 `testdata`。于是
`testdata/` 被当成一个 unittest 套件去跑。

**跑一个夹具不是中性的事**：夹具是**别家仓的样本**，它假设的目录结构本仓
没有，所以它在自己的位置上是 import 不了的 → 套件崩 → 判决变成「无法判定」。

**后果**：**误伤**。报告指名 `test_calc.py`，说它「一个用例都没执行」，让它
「修 import」—— 而 `test_calc.py` 的 import 根本没坏。真正坏的是那个**从
来就不该被运行**的夹具。

而且这个误伤**会掩盖真判决**：同一个仓、同一批提交，夹具没跑起来时工具说
「无法判定」；夹具被跳过之后，它才说出那句真话 ——「撤掉这几行、只留测试
后，2 个测试全部通过」，也就是「这个改动没有测试看着」。

**口径不是新定的**：3.45 已经把「testdata 里的文件不是测试代码」写进了
静态检查那层（`detect.isTestPath`），Go 的包解析那层也早就不看它
（`adapters.skipPackageDir`）。**只有执行这一层还在跑它** —— 两半自相
矛盾：一边说那些文件不是测试，一边把它们当测试跑，跑了还崩溃。

**修复**：套件发现跳过 `testdata`，名字**精确匹配**（`testdata2`、
`testutils` 是普通代码，照样要扫）。顺带把那个目录清单收成一份
（`skipUnittestDir`）—— 原来同一条清单在这个函数里写了两遍。

**负对照**（实测）：

| 改坏的地方 | 变红的用例 |
|---|---|
| `testdata` 不再被跳过 | `TestATestdataDirectoryIsNotASuite`、`TestAFixtureDirectoryDoesNotBreakTheRun` |
| 跳过规则改成前缀匹配（`testdata2` 也被跳过） | `TestATestdataDirectoryIsNotASuite` |

**现场验证**（真仓，不是夹具）：同一个仓，修复前 `suite-crash`（指责真测试
「修 import」），修复后 `vacuous-test`（诚实的判决：没有测试看着这个改动）。

> **一个差点让我误判的细节**：`verdictFrom` 里有一条短路 —— 套件崩了但**别的
> 套件变红了**，以红灯为准。所以「真测试抓得住 bug」的时候，夹具崩溃被
> 淹掉了，判决反而是对的。危害出现在**真测试没抓住**的时候：那时工具本该
> 说「空洞」，却说了「套件崩了」。**所以造复现用例时，先确认方向对不对** ——
> 我第一版把「先坏后修」建反了，工具判「空洞」是对的，我还以为它坏了。

### 3.51 夹具被当成「这次改动带来的测试」—— 判决指错了人，还盖住了真判决

**现象**：一个 Go 仓的 `testdata/` 目录里放着一份**数据夹具**，文件名恰好长得
像测试（`testdata/sample_test.go`）。工具审这个提交，报的是：

```
[HIGH] vacuous-test   testdata/sample_test.go
    这个测试在撤掉修复后依然是绿的 —— 它没有测到修复修的那个行为
    怎么修: 把断言落在可观察的行为上……
    怎么自己验一遍:
    # 2. 只把测试打进去，修复留在外面
    git diff ... -- 'testdata/sample_test.go' > /tmp/vac-verify-tests.patch
```

**根因**：`testdata` 是「测试要用的数据」的约定，**不是测试代码**。Go 工具链
**直接无视**它（`go help packages`：名为 `testdata` 的目录被 go 工具忽略）——
底下的 `_test.go` **永远不会被编译**，所以它既不是测试，也不是代码。

而**判决侧从来没问过这件事**。判决的路径是
`internal/counterfactual/audit.go` → 适配器的 `IsTestPath` / `IsSourcePath`；
适配器那层只有 Go 的**包发现**（`skipPackageDir`）认识 testdata，
**判断一个文件是什么的那一层不认识**。

**这不是 3.45 那个老毛病的第三次复发**：3.45 修的是静态检查那层，3.50 修的是
Python 套件发现那层，**判决那层从来没被修过** —— 只是前两轮没人拿一个 testdata
夹具去撞它。这条判断原来在这个仓里写了**三遍**，而**判决那一遍根本没写**。

**后果**（两层伤害，第二层更贵）：

1. **指控了一个 Go 工具链根本不编译的文件**，还附上「怎么自己验一遍」的配方 ——
   读者照着做，就是去改一份**从来不会被运行**的夹具。
2. **盖住了真判决**。那个提交改了真代码（`internal/greet/greet.go`），
   **没带任何测试**。因为夹具被当成了「这次改动带来的测试」，工具走的是
   「空洞测试」那条路，**从来没能说出那句真话**。

修完之后，同一个提交说的是：`[HIGH] no-test-for-fix  internal/greet/greet.go`
—— 「这个改动改了代码，但没有任何测试跟着来」。**这才是真相。**

第二个复现：只改 `testdata/plain.go` 的提交（连真代码都没碰），修之前报
`[HIGH] no-test-for-fix at testdata/plain.go`（「这个改动改了代码」）——
**假指控**。修之后这个提交**一条发现都没有**：它改的是数据，不是行为。

**修复**：把「什么是 testdata」收成**一份**规则（`adapters.IsTestDataPath`），
所有调用点走它：

| 调用点 | 之前 | 现在 |
|---|---|---|
| `adapters.Go.IsTestPath` | 认 testdata 里的 `_test.go` 是测试 | 不是（go 工具链不编译它） |
| `adapters.Go.IsSourcePath` | 认 testdata 里的 `.go` 是源码 | 不是（它不属于任何包） |
| `counterfactual.isSource`（非 Go 适配器的兜底） | 只按扩展名认 | 不是（testdata 存的是数据） |
| `detect.isTestPath`（静态检查） | 自己写了一份 | 调同一份规则（原来那份删掉） |

外加两个「发现」层：`adapters.skipPackageDir`（Go 包发现）和
`adapters.skipUnittestDir`（Python 套件发现）也改成调同一份规则。

**独立复核又抓出一条同类的**（`verifier` 自己找的改坏点，不是我给的清单里
的）：`discards-error` 这条 **HIGH** 检查仍然指控 testdata 夹具。

`internal/detect/discarded.go` 遍历的是**全部被跟踪的文件**（命令层传的是
`repo.TrackedFiles("HEAD")`），过滤条件只有「后缀是 `.go`」——
**没问过 testdata 这条规则**。结果是：

```
[HIGH] discards-error   testdata/fixture_test.go:7
    错误被丢掉，断言却要求它是空的 —— 加载失败时这条断言照样通过
    怎么修: 别丢掉错误：要么处理它，要么在错误时直接失败
```

这个文件 **Go 工具链根本不编译** —— 跟本轮修掉的那个 bug 是**同一类伤害**：
指控一份「从来不会被运行」的夹具，还附上一张没法执行的处方。

**为什么漏了它**：这条检查**故意**扫的不只是测试文件 —— 同样的形状在普通
源码里也值得知道（仓库 A 那条 `cmd/seed/main.go` 就是）。所以它的过滤条件
不能改成「是不是测试」，只能改成「是不是 testdata」。

修完之后的负对照：`TestTestdataFixturesAreNotScannedForDiscardedErrors` ——
**两头都要钉住**：夹具必须不报，而**真文件里的同一种形状必须照报**
（`store_test.go` 和 `cmd/seed/main.go` 各一条）。只测一头的规则，
「整个检查器被关掉」也能过。

> **这一条本身就是 3.51 那条方法论的证据**：我这一轮把「写过这条判断」的
> 三个地方收成了一份，却漏掉了**一个本该问它**的地方 —— 而那个地方正好是
> **判决之外最贵的一条**（HIGH）。**收敛规则的时候，要问的是「谁在读它」，
> 不是「谁写了它」** —— 没写的地方，比写散的地方更难发现。

**为什么 Python 和 Node 的「是不是测试」不跟着改**：因为它们的运行器**真的会
收集 testdata 里的文件**。实测：`pytest --collect-only` 在
`testdata/test_fixture.py` 上列出了它的两个用例；vitest 默认收
`**/*.test.ts`，同理。**运行器会跑的文件就是测试** —— 把它说成夹具，
下一个后果是「这个提交没带测试」这种**新的假指控**（那个提交确实带了测试）。
所以口径分成两条，而且**必须写清楚是哪一层**：

- **「testdata 永远不是代码」** —— 三个语言都成立；
- **「testdata 不是测试」** —— **判决层**只有 Go 成立，因为只有 Go 的工具链
  给了这个保证。

**静态检查层对所有语言都排除 testdata** —— 方向是**漏报**（少报一条真实的
跳过），换来的是不会把「永远不会运行的夹具」算进这个仓的测试文件清单：
3.50 的教训是跑一个夹具会崩，然后把夹具的锅扣到真测试头上。

**两层对同一个文件给出不同答案，是有理由的**：判决层回答「这个文件会不会被跑
起来」（pytest 说会，那就是测试），静态检查层回答「这个文件是不是这个仓的
测试套件的一部分」（testdata 里的东西是套件的**输入**）。两个问题不同，答案
就可以不同 —— 但**必须写下来**，否则下一轮会把它当 bug「修」掉。

**这条规则的代价，是有意换来的（别当成 bug 修）**：testdata 里的文件**有可能**
被真测试 import —— Python / Node 没有「工具链忽略 testdata」这回事。
实测（Python 仓：`testdata/helper.py` 被 `test_helper.py` import）：

| | 修前 | 修后 |
|---|---|---|
| 只改 `testdata/helper.py` 的提交 | `[WARN] no-test-for-fix testdata/helper.py` | **零发现**（这条真阳性被吞掉） |

方向是**漏报**，符合「宁可漏报不可误伤」。而且要判「这个 testdata 文件到底算
不算代码」，需要 **import 图** —— 静态判断看不到。**不做 import 分析是刻意的**：
猜错了就是误伤（那正是 3.51 开头那条假指控的同款）。

**Go 里没有这个代价**：`go` 工具链保证 testdata 目录**不被编译**，所以它不可能
是任何包的一部分，也就不可能被 import。

**负对照**（7 个改坏点全部实测：改坏 → 变红 → 改回）：

| 改坏的地方 | 变红的用例 |
|---|---|
| 规则本身（名字改成 `testdata_NEVER`） | `TestIsTestDataPath`、`TestGoTreatsTestDataAsNeitherTestNorCode`、`TestSkipPackageDirSkipsTestdataAtAnyDepth`、`TestATestdataDirectoryIsNotASuite`、`TestAFixtureDirectoryDoesNotBreakTheRun`、`TestTestdataIsNotTestCode`、`TestTestdataFilesAreNotCountedAsTests` |
| `Go.IsTestPath` 不再排除 testdata | `TestGoTreatsTestDataAsNeitherTestNorCode`、`TestAuditDoesNotAccuseATestDataFixture` |
| `Go.IsSourcePath` 不再排除 testdata | `TestGoTreatsTestDataAsNeitherTestNorCode` |
| `audit.isSource` 不再排除 testdata | `TestAuditorTreatsTestDataAsNeitherTestNorCode` |
| `detect.isTestPath` 不再排除 testdata | `TestTestdataIsNotTestCode` |
| `discarded.go` 不再排除 testdata | `TestTestdataFixturesAreNotScannedForDiscardedErrors` |
| `skipPackageDir` 不再排除 testdata | `TestSkipPackageDirSkipsTestdataAtAnyDepth` |
| `skipUnittestDir` 不再排除 testdata | `TestATestdataDirectoryIsNotASuite`、`TestAFixtureDirectoryDoesNotBreakTheRun` |

端到端那条（`TestAuditDoesNotAccuseATestDataFixture`）变红时报出来的
**正是生产症状**：

```
--- FAIL: TestAuditDoesNotAccuseATestDataFixture
    the tool made a finding about a data fixture: {Kind:vacuous-test
    Severity:high ... File:testdata/sample_test.go ...}
```

**现场验证**（真复现仓，不是夹具）：修复前后，同一个仓的同一批提交 ——
`[HIGH] vacuous-test testdata/sample_test.go` → `[HIGH] no-test-for-fix
internal/greet/greet.go`；只改夹具的那个提交 → **零发现**。

**6 个被审仓逐条比对**：静态体检 6 个仓 + 审计（仓库 A）**逐条与基线一致**
（改前 / 改后输出 diff 全为空）。修掉的是夹具，没碰到任何真信号。

**一个没动的地方，说明一下**：Python / Node 的「是不是测试」**没动**。实测证明
它们的运行器真的会收集 testdata 里的测试文件（`pytest --collect-only` 列出了
`testdata/test_fixture.py` 的两个用例）—— 那种情况下工具报「空洞测试」是
**真阳性**，不是误伤。这条写进文档，是为了不让下一轮又把它当 bug 修一遍。

**一个已知边界**：`go:embed` **可以**引用 testdata 里的文件（embed 走文件路径，
不走包解析）。所以「testdata 里的文件一定不是代码」这句话对 embed 不成立。
本轮排除的是**文件分类**（不是代码、不是测试），embed 的**宿主文件**
（`emb/emb.go`）照旧算代码 —— 实测 embed 提交的判决不变。唯一的取舍是：
万一有人 `go:embed` 了一个 **.go** 文件，工具不会再为它要求测试。方向是
**漏报**，符合「宁可漏报不可误伤」。

## 4. 两次独立复核

这个项目最大的风险不是「查不出问题」，是「查错了还说得很有把握」。
所以除了 dogfood，还做了两次**独立复核** —— 一个不知道结论的 agent 去查
「我的负对照是不是真的」。

### 4.1 复核一：假负对照

**做法**：把被守护的规则改坏 → 跑守护它的测试 → 看它是否真的变红。
改坏了仍然全绿的，就是假负对照。

**25 条关键规则里 25 条改坏就红** —— 这一半的纪律是真的，而且扎实。

**但有 5 处是假的或缺失的**，全都已修：

| # | 洞 | 为什么危险 | 修法 |
|---|---|---|---|
| ❶ | 环境判定的**模式表**整张没有负对照 | 那条测试**因错误的原因通过**（错误串没有「文件:行:列」的形状，函数落到兜底分支）。把整张表删空，它照样绿。而这张表决定的正是 environment 和 coupled —— **含义相反的两个结论** | 补了一条真会走到那张表的用例；清空表后测试变红 ✅ |
| ❷ | **skipped 判定从来没有被测过** | `VerdictSkipped` 在全部测试里出现 **0 次**。而它的 finding 是**严重级**：「测试没有执行 —— 它一次都没跑过，所以什么都没证明」。一个从没跑过的测试会被判「绿」，然后被高危指控 —— **和最初那次事故同形，却更安静** | 补了 5 条：全 skip → skipped；**全 skip 绝不能判 vacuous**；混合情况按真跑了的那些判；finding 必须严重级；空 run 也算 skipped |
| ❸ | 归档检出的「精确性」保证没有负对照 | 全仓**没有任何 fixture 带 `export-ignore`**，所以「检出 == 树」这个比较怎么都成立。README 写着「工具永远知道自己手里的检出是不是精确的」—— 没有任何测试兜着 | 加了带 `export-ignore` 的 fixture；拆掉守卫后测试变红 ✅ |
| ❹ | 「.git 一个字节都不碰」没被测 | 那条测试比的是 **Remove() 之后**的指纹 —— 证明的是清理干净了，不是过程里没写。换成 `git worktree add`（代码注释里明确排斥的做法）**照样绿** | 改成在检出**还活着**的时候比指纹；换机制后测试变红 ✅ |
| ❺ | 「工具反对自己」的自检**接线和整条路径都不可达** | 它拿「判定」和「计数」比 —— 同一个来源，比不出东西，四个条件在 classify() 的任何返回值下都不成立。**是死代码** | 改成拿**运行器自己的原始输出**比（唯一没经过解析器的独立来源），并挪进 classify() 内部；短路线后测试变红 ✅ |

**顺带修了一个真 bug**：编译错误的文件路径提取，行首的「包名: 」前缀会把真正的
「文件:行:列」粘掉。改用正则直接扫。

### 4.2 复核二：Node 适配器在真实仓库上

在两个公开仓上实测（`tj/commander.js` 用 jest、`antfu/local-pkg` 用 vitest），
找到 **5 个真 bug**（都已修）+ **4 个待办**（已记成 issue）。

| # | 问题 | 后果 |
|---|---|---|
| ❶ | 符号链接被**跟随**，pnpm 布局下 `node_modules` 复制中途夭折 | 实测只复制了 **0.9%**，而复制错误**被吞掉** —— 工具报「代码缺东西」，把读者指向完全错误的方向 |
| ❷ | `.bin` 里的 runner 入口被拷坏 | 跟随链接把「目标的内容」写进「链接的路径」→ 相对 import 失效。**同一份代码对 jest 成立、对 vitest 直接坏** |
| ❸ | 复制失败被吞 | 见 ❶ |
| ❹ | `xit(` 匹配到 `process.exit(` | 真实仓上因此报了 5 条假「测试被跳过」，证据全是 `process.exit(2);` |
| ❺ | 复用 workflow 被判成「CI 不跑任何测试」 | 看**看不到**不等于**没有** —— 工具现在说「看不出来」，不下那个结论 |

**待办**（issue #5–#8）：Node 只跑改动的测试文件导致假阴性、套件崩了被当成
环境问题、test script 内容被丢弃、`test/` 目录下的 `.mjs` 被当源码。

**这次复核最有价值的一条**：**它证明「夹具测试全绿」不等于「适配器能用」**。
pnpm 布局、相对 import、复用 workflow、jest 与 vitest 的差异 —— 这四件事
夹具一个都测不到，只有真跑才会撞出来。

## 7. 验证链条

---

一次交付要同时过四道：

1. **单元 / 集成测试** —— 每个检查器都有负对照（把规则拆掉，测试必须变红）
2. **clean-room** —— `git clone` 到全新目录，**断网**（`GOPROXY=off`）构建 + 全测。
   零第三方依赖意味着连 `go.sum` 都不需要。
3. **端到端冒烟** —— 用 clean-room 出来的二进制跑真实仓库和合成仓库
4. **CI** —— Linux + detached HEAD + 空 module 缓存。本机能过不算数：
   CI 才是它唯一必须成立的地方

CI 里有两个 job：`build`（fmt / vet / build / test -race / 空缓存 test）和
`self-check`（用 vacuous 审 vacuous 自己）。

> **2026-10-20 21:xx 补一句**：修 3.19 之前，`self-check` 这个 job **是个
> 装饰品**。这个仓有 4 个嵌套 module（testdata 夹具），于是根 module 的测试
> 一次都没跑过，审每一笔提交都得出「environment」，INFO 级 ——
> `--fail-on critical` 永远不会触发。修完之后它才真的在审东西。
>
> **2026-10-21 12:xx 补一句**：修 3.29 之前，`self-check` 还会**审出自己
> 的误报** —— 仓里那笔 `docs: 脱敏` 只改了一行注释，却被判成「空洞测试」。
> 修完之后这个仓自己的结论是 `proven 5 · vacuous 0 · 无测试 2 · 无法判定 9`，
> `空洞` 从 1 变成 0。**工具审自己审出了自己的误报，而且只有把规则挪对了
> 位置才会消失** —— 这条比上面那条更值得记一笔。
>
> **2026-10-21 16:xx 再补一句**：上面这行数字**已经过期**，因为 3.30 把
> 默认窗口修好了 —— 之前 self-check 审的是**全部历史**，现在只审最近 20 个
> 提交。同一时刻的数字变成
> `proven 4 · vacuous 0 · 无测试 0 · 无法判定 9 · 不适用 6`。
> 两件事要一起记：**窗口**（审多少）和**判定**（审出什么）是两回事，
> 窗口变了数字就会变，而数字一变就得说清楚是哪一边变的。
>
> 剩下的 1 条 environment 是 `a5b4e3b`（仓库改名、模块路径跟着换的那笔）。
> 它的反事实树是「旧模块路径 + 新 import」，两半凑不到一起，于是测试跑不起来
> 又说不出原因。判成「判不出来」是对的 —— 这个方法对「改模块路径」这类提交
> 本来就笨，诚实地说不出来，好过硬给一个结论。

## 8. 这份文档没有覆盖的东西

- **n = 1 的仓**：6 个仓库、约 120 次运行。所有「真阳性」的结论都是人工
  逐条核实的，但样本量摆在这里，说不上统计显著。
- **耦合判定的精度**：`⟨sha⟩` 判对了，但那是唯一一个手工拆开验证过的
  耦合案例。7 条 coupled 里其余 6 条没有逐一复核。
- **coupled 的成因没有分类**：仓库 A 那 7 条 coupled 里，大部分是「测试引用了
  这次修复才引入的符号」—— 撤掉修复后测试编译不过。这在源码层面无法拆开，
  是这个方法本身的边界，不是工具的缺陷。但工具目前只给一个笼统的 coupled，
  没有区分「测试用了新 API」和「别的原因编译不过」。
- **Python / Node 适配器的真实仓库验证**：Python 已经在 仓库 I 上
  跑通（见第 4 节）。**Node 仍然没有靶子** —— 本地四个 Node 仓都没配测试
  运行器，所以 jest / vitest 的反事实路径只有夹具测试覆盖，从未在真实仓库上
  跑通。这是最大的已知空白。
- **多 module 场景**：仓库 C 有 7 个独立 module。**修 3.19 之前它其实
  根本没被审过** —— 根 module 的测试一次都没跑过，审出来的是夹具的结论。

  但里面 25 条 environment 说明这套反事实在「一堆小 module 的实验仓」上很吃力：
  多数提交判不出来。还没有在「多个 module 中只有一个有测试」的仓库上验证过。
- **静态检查层与判决层对 testdata 的口径不同**（3.51 写明的刻意选择）：
  判决层按**运行器的实际行为**判断（pytest 收集 `testdata/test_fixture.py`，

  与 3.51 无关，但它的后果是：Node 路径目前**产不出** `vacuous` 判决，
  3.51 那条「testdata 里的 Node 测试仍然算测试」只在**工具层**验过
  （`IsTestPath` 认它、把它放进测试命令、不报 `no-test-for-fix`），

**两条关于负对照本身的教训**（都是这一轮现场撞上的）：

1. **测函数 ≠ 测接线。** 「同一个测试只算一次」这条规则，第一版只测了

   计数还是错的。改成**驱动一次真实运行**、看报告里实际握着的结果，才算

2. **一条规则一个用例，包括「为什么它重要」。** 「根套件离任何改动都近」
   这条规则本来一条负对照都没有：它坏了不会让任何测试变红，而它坏了的后果
   是「根目录的测试不再跑」→ 工具会把一个**真的在看守修复**的测试判成

「有没有把*这个仓*说成 unittest 项目」，原意一点没丢。

### 3.42 手工验证一条 proven —— 既存的红灯被正确排除

**为什么手工验**：工具的每个判定都是「跑出来的」，但读者没法自己看那两棵树。
一次端到端的手工复现，是唯一能证明「它认出来的那个看守是真的」的办法。

**场景**：一个 Python 仓（用 unittest）的某个提交。工具判 **proven**。

**手工复现**（按工具自己给的配方）：

```
# 反事实树 = 父提交 + 只打测试补丁（修复留在外面）
git archive <commit>^ | tar -x -C /tmp/verify
git diff <commit>^ <commit> -- 'scripts/test_build_docs_site.py' | git apply
cd /tmp/verify && python3 -m unittest discover -v -s scripts -t scripts -p 'test_*.py'
```

**结果**：

| | 反事实树（修复在外） | 基线树（这个提交自己的树，带修复） |
|---|---|---|
| 失败用例 | 5 个 | 2 个 |
| 那个提交新加的测试 | **红**（1 个 error + 2 个参数化 fail） | **绿** |
| 缺子模块 `example-access/docs` | 红 | 红 |
| 另一个模块的 Python 3.9 f-string 语法 | 红 | 红 |

**集合差正好是那个提交新加的测试文件的 3 个用例** —— 全都因为撤掉修复而红。
两个**既存**的红灯（缺子模块、Python 版本语法）两边都在，**被正确排除**。

**这就是「比集合不比数量」要解决的东西**：这个仓的套件本来就有 2 个红灯，
一个只比数量的实现会把它们算进「撤掉修复弄红的」里。这个实现不会。

也说明一件事：**「proven」这个判定本身是可以被第三方独立复核的** —— 工具把配方
写进报告，读者照着跑就能看到那两棵树分别红在哪。配方不准，结论就作废。

### 3.52 「空洞测试」这个判定冤枉了测试，而且喊得太响

**问题**：这个判定说的是「撤掉修复后没有测试变红」。它**从来没说过**
「这个测试是坏的」。

但报告写的是「这个测试在撤掉修复后依然是绿的 —— 它没有测到修复修的那个行为」，
**严重级 high**。读起来就是「你的测试是废的」，读者的下一个动作是去改一个
本来没问题的测试。

**实测（16 个真实仓，124 条发现）**：

| 类别 | 条数 | 严重级 |
|---|---|---|
| no-test-for-fix（改了行为没测试看着） | 13 | **high** |
| no-test-for-fix（只加测试 / 只改注释，无害） | 13 | info |
| coupled | 11 | warn |
| not-applicable | 57 | info |
| environment | 26 | info |
| pre-existing-failure | 4 | info |

**空洞测试在 example 那 14 个仓里一条 high 都没有。** 真正被当作紧急问题报出来的
是「改了行为但没有测试看着」—— **同一件事，只是说在改动上，而不是说在测试上。**

而公开仓上那 3 条空洞测试，逐条查过：

| 提交 | 真相 | 工具怎么说 |
|---|---|---|
| 86b00a4 | 删的是**别处早就有一份的重复代码**（活的版本在另一个包里，父提交里一个调用点都没有）→ **行为一点没变** | **high：空洞测试** |
| 8a97fe6 | 源改动是真的（把中断消息攒起来一次写）→ **改动没人看**（真缺口） | high：空洞测试（标签冤枉了那个测试） |
| moby 那个 | 改动只有 2 行 | warn：改动很小（工具自己降级了） |

**第一条是纯噪音**：那个提交什么都没改，工具却喊了 high。

**根本原因**：这个判定在**原理上**分不出「重构」和「真行为变更没人看守」——
两者的测试表现**完全一样**（都绿）。工具能说的只有「撤掉修复后测试没红」。

**三处改动**：
1. **措辞**：不再说「这个测试是空洞的」（指控那个测试），说「**这次改动没有测试
   看着它**」（陈述这次改动）。读者该做的动作一样（补测试），但不会去改一个
   没问题的测试。detail 里明说「这不等于那个测试是坏的」。
2. **严重级**：high → warn。一个「没测试看着」通常不是紧急事；而且实测里有
   纯噪音被判成 high。
3. **识别去重**：提交只删代码、且被删的函数在树的另一个地方还有一份声明 →
   那是去重/移走，**行为没变** → 降成 info，标题写「这次改动只是把别处已有的
   代码删了一份 —— 行为没变」。

**第 3 条只能是启发式，而且偏保守**：被删的函数名相同但在不同包，那是同名不同物，
所以这条检查宁可漏报（少一条发现），不误伤（把真缺口吞掉）。要完全判准，需要
「被删的函数本来就没有调用点」这种类型级信息 —— 静态分析能给，工具现在给不了。

**真实数据上的验证**：terraform 的 86b00a4 从「严重级：这个测试是空洞的」变成
「信息级：这次改动只是把别处已有的代码删了一份 —— 行为没变」。

**负对照**：把去重判定关掉 → `TestAuditDoesNotAccuseADeduplication` 变红；
把严重级改回 high → `TestAuditDetectsVacuousTest` 变红。

### 3.53 方法的名字被读成了关键字 `func` —— 去重判定见方法就说是去重

**问题**：去重判定（3.52 的第 3 条改动）要把「被删掉的函数」和「树里剩下的
函数」对上号。它先把补丁里被删的函数名读出来，再拿这个名字去树里找。

**根因**：读名字的那段代码把声明切在**第一个**左括号上：

```go
open := strings.Index(decl, "(")   // 方法的接收者才是第一个左括号
head := strings.TrimSpace(decl[:open])
head = strings.TrimPrefix(head, "func ")
if strings.HasPrefix(head, "(") {  // ← 这一支永远进不去
```

方法的写法是 `func (s *Store) Helper() int`。切在接收者的左括号上，
`decl[:open]` 就是 `"func "` —— 去掉空格后是 `"func"`，而
`TrimPrefix(head, "func ")` 要的是**带空格**的 `"func "`，所以什么也没去掉。
接着 `HasPrefix(head, "(")` 问的是**接收者那个左括号之前**有没有 `"("`，
按定义不可能有 —— **处理接收者的那一支是死代码**。

结果：**每一个方法的名字都读成了字符串 `"func"`**。

```
"func Helper() int { return 1 }"            -> "Helper"
"func (s *Store) Helper() int { return 1 }" -> "func"     ←
"func (o *Other) Method() int { return 2 }" -> "func"     ←
"func Foo[T any](x T) T { return x }"       -> "Foo[T"    ← 泛型把类型参数带进了名字
```

**为什么这条特别毒**：`"func"` 不是标识符，是关键字。它和**树里每一个方法**
都「同名」。于是「删掉了一个方法」这个提交，在任何一个还有别的方法的 Go 仓里，
都会被判成「别处早就有一份 —— 行为没变」，严重级降到 info。

**实测**：把 `funcDeclName` 换回旧实现，跑新加的端到端夹具，工具报的是：

```
这次改动只是把别处已有的代码删了一份 —— 行为没变        （info）
```

真相是：这个提交删掉的是 `func (s *Store) Helper()`，树上**没有任何**叫
Helper 的方法留下来 —— 被删掉的那一个本身就不在了。**报告在说一件假事**，
而且因为严重级被降到 info，一条真的发现被顺手当成了脚注。

**修复**：按声明的三种形态分别读名字 —— 普通函数、带接收者的方法、
带类型参数的泛型函数。接收者那一段要**数括号**：`func (f func() int) Call`
这种接收者本身是函数类型的，写法上会骗过「找第一个右括号」。

**负对照**：`TestAuditDoesNotCallADeletedMethodADeduplication`。
把 `funcDeclName` 换回旧实现 → 变红（报的是「行为没变」+ info）；
换回新实现 → 绿。原来那条 `TestAuditDoesNotAccuseADeduplication` 在两种实现
下都绿 —— 它没被这次改动带偏。

**连带更正 3.52 的两处**（3.52 是上一轮写的，那两句话当时是错的）：

1. **3.52 说 terraform 的 86b00a4 是「删的是别处早就有一份的重复代码」** ——
   不对。那个提交删的是**两个方法**：
   `func (m *Meta) defaultFlagSet(n string) *flag.FlagSet` 和
   `func (m *Meta) extendedFlagSet(n string) *flag.FlagSet`。
   `arguments` 包里活着的版本是**另一个函数**：没有接收者、参数叫 `name`
   而不是 `n`、`ioutil.Discard` 换成了 `io.Discard`，而且它**不设 Meta 的
   那些字段**（`m.input` / `m.targetFlags` / `m.compactWarnings` / `m.stateLock`）。
   那是**重写**，不是复制。
   结论（这个提交没改行为）**碰巧是对的** —— 提交说明里写明那两个方法
   「as they are unused」。但工具给出的**理由**是假的：它对上号靠的是
   `"func"` 匹配到树里随便哪个方法，跟被删的那两个方法没有任何关系。
2. **3.52 说「被删的函数名相同但在不同包，那是同名不同物，所以这条检查宁可
   漏报」** —— 代码里**从来没有比过包名**。`funcExistsOutside` 只看函数名，
   加上「这个文件不是补丁碰过的文件」。这条保证写在文档里，不在代码里。

**修好之后 terraform 的 86b00a4 变成什么**：去重判定**不再命中**
（`extendedFlagSet` 是小写的、包私有的方法，不可能有同名的东西在另一个包里；
而 `defaultFlagSet` 虽然同名，签名和函数体都不一样）。所以这个提交回到
「这次改动没有测试看着它」（warn）。

**这是不是把 3.52 修好的东西又弄坏了**：不是。3.52 的**严重级**改动
（high → warn）和**措辞**改动（「说这次改动，不说这个测试」）跟去重判定是
**两件独立的事**，它们站得住：16 个真实仓的实测里，「改了行为没测试看着」
本来就是该喊的那一类。修掉「读名字」这个 bug 之后，86b00a4 仍然**不是**
high，只是从 info 变成 warn —— 正是 3.52 想要的语气。

**还剩的代价**：去重判定**只比名字**。同名但函数体不同的两个函数会被当成
一对。Go 的编译器挡住了大部分会出错的场合（被删的代码如果还有人用，HEAD
就编译不过，工具跑不到这条路），但这条保证是**编译器给的，不是这个判定
给的**。要把判准做实，需要「被删的函数本来就没有调用点」这种类型级信息。

**验证**：改前改后在 6 个被审计仓上跑 `--mode check`、在 alpha 上跑
`--mode audit`，输出**逐字节相同** —— 这条路径在那 6 个仓上没有被触发过
（alpha 的空洞测试条数是 0）。

### 3.54 定时校验任务的闸门指令还在用旧基线 —— 每轮都会误判「有变化」

**现象**：2026-10-22 中午这一轮核验，闸门（`scripts/gate.sh check`）报「没变化」，

| 判据 | 期望 | 实际 |

| 旧指令（拿 DOGFOOD.md 里的基线 commit 比） | 判「没变化」 | **判「有变化」**（`df223ea` ≠ HEAD）—— 每轮都误报 |

闸门一模一样。本轮拿状态文件当靶子做了两次负对照（改完立刻**字节级还原**，

| 篡改 | 期望 | 实际 |
|---|---|---|
| 状态文件里的指纹 | 报「工具代码变了」 | `[code]` + 退出码 1 ✅ |
| 状态文件里仓库 B 的 HEAD | 报「被审仓库动了」 | `[target]` + 退出码 1 ✅ |
| 还原之后 | 回到「没变化」 | `NO CHANGE` + 退出码 0 ✅ |

照样误报「有变化」，又白跑一轮。完整的顺序是：改 → 测 → 补负对照 → 更新本文 →
**提交并推送** → 刷新基线 → 确认 `gate.sh check` 说 NO CHANGE。

**这次不动工具代码**：只改定时校验任务的指令正文 + 这份文档。代码指纹因此不变 ——
闸门下一轮仍然安静，这正是 3.18 要的（改文档不该让基线失效）。

### 3.44 反事实树里留着修复 —— 空路径列表被当成了「全部文件」

**这是本项目最要命的一个 bug。**

**现象**：`git.Patch(sha, paths)` 在 `paths` 为空时**没有加路径过滤**，
于是 `git diff` 返回的是**整个 diff**。而反事实实验打进去的正是这个 patch。

调用方传空列表的地方只有一个：这次提交**自己没带测试**的时候（测试侧路径
列表为空）。于是：

- 反事实树 = 父提交的树 + **整个提交（含修复）** = 提交本身
- 工具跑的是**带着修复的代码**，然后据此说「撤掉修复后没有测试变红，所以
  没有测试看守这个行为」

**后果**：「这个改动改了行为，但没有任何测试看守它」这条**高危、可拦门禁**的
发现，它的全部证据都来自一次**带着修复的运行**。那条证据是空的。

**更要命的是 TDD 流程**：测试提交在前、修复提交在后 —— 修复提交自己不带测试，
于是工具把它判成「没人看守」（高危）。而看守它的测试**就在上一个提交里**，
它**确实**在撤掉修复后变红。**TDD 团队每改一次代码都会被拦一次。**

**怎么找到的**：外部评审指出「没修改测试文件，就直接报没带测试」，说它不会
运行已有测试验证保护关系。顺着查下去，发现的不是「少做了一步实验」，而是
**实验做的是另一棵树**。

手工复现（一个两提交的仓：先提交测试、再提交修复）：

```
提交 1:  buggy 源码 + 会失败的测试
提交 2:  修好的源码（不带测试）
```

- 手工搭反事实树（`git archive HEAD^`）→ 那个测试**是红的** ✓
- 工具的反事实树 → **修好的源码**，那个测试是绿的 ✗

**修法**：
1. `git.Patch` 的空路径列表表示「**没有文件**」，不是「所有文件」。契约本来
   就写着 "restricted to paths"。生产代码里没有任何调用方需要「全部」
   （要全部的地方自己拼了 git 命令），所以改契约是安全的。
2. 自己不带测试的提交，**照样跑反事实**，但范围放宽到**整个模块** ——
   因为要回答的是「仓里**任何**现有测试守不看守这个行为」，看守它的测试
   常在别的包里。
3. 结果分两种：现有测试**变红** → 普通的 proven（这正是 TDD 流程该有的判定）；
   **全绿** → 「没有任何测试看守这个行为」，而且这次是**实验结论**，不是猜测。

**修完之后**：那个 TDD 仓的判定从「no-test（高危）」变成 **proven** ✓

**负对照**：把空列表改回「全部」→ `TestAuditFindsAGuardFromAnEarlierCommit` 变红。

**教训**：「一个函数在某个参数组合下行为不对」比「一个函数没被调用」难查得多。
`Patch` 的空列表语义在**所有**有测试文件的提交上都是对的 —— 那些提交的反事实
一直是对的。**只有「这次提交没带测试」这一条路径是错的**，而那恰好是工具
最想说点什么的那条路径。

### 3.45 审不了的提交，退出码是 0

**现象**：传一个不存在的 commit，报告里所有计数都是 0，而且**退出码 0**。
CI 门禁会放行。

**根因**：审不成的时候，工具加了一条 **warn 级**的发现（还被打扮成
`coupled` —— 那是在指控测试），低于默认门槛 `high` → 退出码 0。

**后果**：这正是这个工具存在的意义被反转的那一刻 —— 「我没能审」和「没什么
可审的」在门禁眼里长得一模一样。

**修法**：
- 自己的 kind（`audit-failed`），不是「coupled」—— 它不是关于代码的结论，
  是关于**报告**的结论：报告里有个洞。
- 报告里有计数（`audit_failed`）。
- **退出码 2** —— 这个工具早就为「判不出来」留的码 —— 而且**优先于**严重级
  规则：报告里有个洞的时候，它就不是一份完整的报告。

**外部评审发现的**，提法很准：「审计失败可能仍然绿灯」。

**负对照**：去掉退出码规则 → `TestAuditOfACommitThatCannotBeReadFailsClosed` 变红。

### 3.55 「实验没跑起来」被说成了「没有任何测试看守它」

**现象**：一个自己不带测试的提交，工具给出**高危**发现：

> 把这次修复撤掉之后，仓里**现有的**测试全部通过（**0 个通过**、0 个失败、0 个跳过）——
> 也就是说，没有任何测试看守这个行为。

一个测试都没跑，却说「全部通过」。

**根因**：判断「仓里有没有东西看守这个行为」用的探针是**失败数**：

```go
if !shippedItsOwnTest && countFailures(run.result) == 0 {
```

而**编译不过的树，失败数恰好是 0** —— 编译失败的包不产生失败的测试，它产生的是
**一个都没跑**。于是：

- 反事实树编译不过 → 判定本来是 `environment`（「判不出来」）→ 被这行覆盖
- 覆盖成 `VerdictNoTest` + 高危指责

**树里没编译过去，恰恰是最不能下结论的情形**：那些没跑起来的套件，正是可能
看守这个行为的那几个。

在真实仓（仓库 A）上抓到一条：那个提交的反事实树里有一个包编译不过（它依赖
一个没入库的生成物），工具照样给了「没有测试看守它」。手工复现确认：反事实树
里 `go test ./...` 报 `FAIL <pkg> [build failed]`，一个测试都没执行。

**修法**：探针换成**判定**本身。

```go
if !shippedItsOwnTest && res.Verdict == VerdictVacuous && !run.deduplicated {
```

`VerdictVacuous` 的意思是「实验跑完了，全绿，而且运行器自己的输出没有反着说」。
其他判定（environment / coupled / suite-crash / skipped / contradictory）都是
**没有答案**；「没有答案」不能被写成「答案」。

顺带修掉的：
- 这条发现的**证据**原来只有一行命令 —— 读者看不到那个 `build failed`；现在
  和别的发现一样带上运行输出，**复现步骤**也从空的变成有的。
- `res.SourceChange`（改动大小）在这条路径上没被赋值，报告里丢了这个信息。
- `Patch` 的接口契约注释还写着「空路径列表 = 整个提交」，和 3.44 改掉的实现
  对不上；`AuditCommit` 的注释还写着「没有测试就是一条发现」。

**改完之后的第二个坑**：一个**连测试文件都没有的仓**被静音了 —— 那恰恰是
工具最该说话的时候。原因是这类仓的反事实树跑不出任何测试用例，判定成了
`environment`。

**两种「没跑」必须分开**：
- **树里一个测试都没有** → 答案在跑之前就知道了：没有东西能看守这个行为 →
  照说（高危）。用 `TrackedFiles` 数父提交里的测试文件。
- **树里有测试但跑不起来** → 没有答案 → 不说。

但这一步只对**适配器有权威**的语言成立：Go 的工具链只跑 `_test.go`，规则
就是全部答案；Node / Python 由 jest / pytest 的配置说了算，文件名规则只是
**猜**。所以加了 `TestDiscoveryIsAuthoritative` 这个能力接口 —— Go 答 true，
Node / Python 答 false，后两者继续由实验来回答。

**负对照**：
- 把探针改回失败数 → `TestAuditDoesNotAccuseWhenTheExperimentCouldNotRun` 变红。
- 去掉「树里没测试」这条分支 → `TestAuditSaysSoWhenTheTreeHasNoTestsAtAll` 变红。

**教训**：**「没有失败」和「全都通过」是两件事**，而只有后者能撑住一句指责。
在一次没跑起来的实验上得出「没有测试看守它」，是把**证据的缺失**当成了
**证据**。判断一个实验有没有答案，问的应该是实验**判定**了什么，而不是它
**数到了几个失败**。

### 3.56 超时测试的预算只有 5 秒 —— 它测的是机器，不是工具

**现象**：全量测试偶尔挂在 `TestParallelAuditRecordsATimeoutWithoutDraggingTheRound`：

```
the ordinary commit: expected verdict "proven", got "timeout"
```

**根因**：这个测试给并行审计器的预算是 **5 秒**，而预算是「一次提交的整个
审计」的时限 —— 检出、打补丁、跑测试都算在里面。那个「普通提交」只需要跑一个
两文件模块的 `go test`，空闲机器上不到半秒；但**机器一忙**（CI 跑全套、
本机同时在跑几个仓的 dogfood 审计），它自己的运行就会被 5 秒掐断。

于是断言测的是**机器有多快**，不是工具做得对不对。

工具本身在那次是**对的**：它把被掐断的运行记成 `timeout`，而不是拿半截输出
编一个判定。错的是测试的预算。

**复现方式**：一次全量测试和 4 个仓的 dogfood 审计同时跑 → 挂；单独跑 → 绿
（本轮 5 次全量：1 挂 4 过）。

**修法**：预算 5 秒 → 20 秒，「这一轮不能等太久」的上界 20 秒 → 40 秒。
断言**一个字没松** —— 仍然是「普通提交必须被判成 proven」「挂起的那个必须
被记成 timeout」。

**负对照**：把预算改到 300 秒（挂起测试因此不会被掐断）→ 测试变红。说明放宽
的是预算，不是断言。

**教训**：给真实测试运行设的**墙钟预算**必须留够机器变慢的余量。
「工具在 5 秒内没跑完」和「工具跑不完」是两件事，测试要断言的是后者。

### 3.57 「只读保证」只管住了 git，没管住 go —— 审计把被审仓库的 go.sum 改了

**现象**：仓库 A 的工作树里，`go.sum` 多了 144 行 —— 整个模块图的哈希，
`charmbracelet/glamour`、`ProtonMail/go-crypto`、`atomicgo/cursor` 这些
**构建根本用不到**的传递依赖。

这不是开发者写的代码，是**审计留下的**。

**根因**：Go 适配器给子进程设了 `GOFLAGS=`，注释写的是「让这次运行保持隔离：
环境里一个野 GOFLAGS 会改变被测的东西」。**空字符串不是「清掉」** —— Go 把
**空的**环境变量当成「没设」，于是回落到用户的配置文件（`go env -w`，默认
`~/Library/Application Support/go/env`）。而这台机器的配置里正是：

```
GOFLAGS=-mod=mod
GOPROXY=https://goproxy.cn,direct
GOSUMDB=sum.golang.google.cn
```

`GOFLAGS=` 于是**什么都没挡住**：子进程照样跑在 `-mod=mod` 下 —— 而
`-mod=mod` 明确允许 go 命令改写 `go.mod` 和 `go.sum`。

更要命的是另外两处 `go list`（`go_run.go` 里问「这个测试来自哪个文件」的那次，
和 `modules.go` 里问「这个 module 有没有这个包」的那次）**根本没设环境**，
`cmd.Env` 是 nil → 整个继承调用方的环境。而审计规程要求的就是
`GOFLAGS=-mod=mod`。

**后果是三件事叠在一起**：

1. **只读保证是假的**。README 写着「审别人的仓库时，工具一个字节都不写进去」。
   实际上 `check` 模式是在被审仓库的**工作树里就地**跑的，`go test` /
   `go list` 在 `-mod=mod` 下可以改写它的 `go.mod` 和 `go.sum`。
2. **同一个仓，两台机器两个结论**。CI 的机器配置里没有 GOFLAGS → 默认
   `-mod=readonly` → 只读；这台机器 → `-mod=mod` → 可写。同一份审计，
   在本地和在 CI 上跑的不是同一种东西。
3. **闸门看不见**。3.23 写明闸门**有意**不看被审仓库的工作树（仓库 D 一直有
   未提交的在制品，算进去就每轮都喊「有变化」）。于是这类污染**天然不可见** ——
   被审仓库的工作树和它提交态不一样了，没有任何一层会说话。

**复现方式（工具之外的手段）**：

```
$ git -C 仓库A show HEAD:go.sum > /tmp/committed.go.sum   # 126 行
$ cd 仓库A工作树 && GOFLAGS=-mod=mod GOPROXY=off go mod download all
$ wc -l go.sum                                           # 270 行
$ diff go.sum 仓库A工作树/go.sum                           # 完全一致
```

`go mod download all` 在 `-mod=mod` 下写出的 `go.sum`，和工作树里那份**逐字节
相同** —— 污染的来源和机制都对上了。同一个目录用 `-mod=readonly` 跑，
`go.sum` 一个字不动。

另外两条（同样是工具之外的验证）：

```
$ GOFLAGS= go env GOFLAGS
-mod=mod            # 空字符串没挡住配置文件
$ GOFLAGS= GOENV=off go env GOFLAGS
                    # 空了
```

**修法**：新增 `goToolEnv()`，**三处** `go` 调用统一走它：

```go
func goToolEnv() []string {
	return []string{
		"GOFLAGS=",
		"GOENV=off",   // ← 真正堵住的那一行
		"GO111MODULE=on",
	}
}
```

`GOENV=off` 让 Go **完全不看配置文件**，于是 `GOFLAGS=` 才真的是「哪儿都没有
GOFLAGS」，子进程回落到 Go 自己的默认值（`-mod=readonly`；模块自带
`vendor/` 的话是 `-mod=vendor`）。三处分别是：plan 的环境（`go test`）、
`go_run.go` 的 `go list`、`modules.go` 的 `go list` —— 后两处改成走新的
`goCommand()` 辅助函数，不再继承调用方的环境。

**修的过程中踩到的第二个坑（差点当成别的毛病）**：`cmd.Env` 一旦被**显式**
设过，`os/exec` 就不再往里面注入 `PWD=<工作目录>` —— 那个注入只在
`cmd.Env == nil` 时发生。于是子进程带着**别的目录**的 PWD 启动，`go` 工具
只好回落到系统调用去拿当前目录，顺手把软链解开：macOS 的
`/var/folders/...` 于是变成 `/private/var/folders/...`。

报出来的路径和工具问的路径对不上，`relToRoot` 认不出来 → **范围映射整个
是空的**。症状是两条早就存在的测试突然变红：

```
TestGoAdapterRunsRealSuite: TestAdd file = "", want "add_test.go"
TestGoScopePatterns: goScopePatterns = [], want [./ ./internal/calc/...]
```

修法：`goEnvFor(dir)` 里把 `PWD=<dir>` 一起带上（`go test` 那一路同样补上），
把 `os/exec` 替我们做的事自己做掉。

**负对照**：

1. 把 `GOENV=off` 那一行删掉 → 两条测试一起红：
   - `TestGoToolEnvIgnoresTheGoEnvFile`：报「go 子进程从机器的 go 配置文件里
     继承了 GOFLAGS="-mod=mod"」—— 它自己造了一台「配置里有 -mod=mod」的机器
     （一个假的 go env 文件），所以**在任何机器上都会红**，不只在这台上。
   - `TestGoListDoesNotWriteGoSum`：**端到端地**把被审仓库的 `go.sum` 改写出来
     —— 报的就是那两行哈希。测试用的依赖由一个本地 `file://` 代理提供，
     不需要网络，也不碰共享的模块缓存。
2. 把 `PWD=` 那一行删掉 → 三条测试一起红：上面那两条，加上
   `TestGoListReportsThePathWeAskedAbout`（它自己造一个指向检出目录的**软链**，
   要求 go 工具报回来的路径落在软链这条路径上 —— 不依赖平台：macOS 的临时目录
   本来就在 `/var` 底下，Linux 上不是，所以测试自己造软链）。

改回去 → 全绿。

**教训**：

- **显式设环境会悄悄改掉别的行为**。`PWD` 的注入是 `os/exec` 的副作用，
  不是承诺：一旦 `cmd.Env` 非 nil，它就没了。改环境的时候要连带问一句
  「这个子进程原来还依赖什么」。
- **两处路径长得不一样，要按「是不是同一个目录」比，不能按字符串比** ——
  软链、`/private` 前缀、`/tmp` vs `/private/tmp` 都是同一类。

- **把环境变量设成空，不等于清掉这个环境变量**。Go 会把空的当「没设」，回落
  到配置文件。想真的「哪儿都没有」，得让那份配置根本不被读 —— 这就是
  `GOENV=off` 的用处。审计规程（`GOFLAGS=-mod=mod`）和工具的隔离要求
  （`GOFLAGS=`）正面撞车时，输的是工具：**隔离必须赢**，而且要赢得**不依赖
  调用方怎么设**。
- **只读保证要覆盖整条链，不只是 git 那头**。3.x 里反复写的是「用
  `git archive` 而不是 `git worktree add`」 —— 那是 git 那一头。这一条漏掉
  的是**工具链那一头**：`go test` 一样能在你的仓库里落字。
- **闸门有意不看被审仓库的工作树**（3.23）是对的，但它有个前提：被审仓库的
  工作树**只被开发者改**。工具自己往里写，就把这个前提打破了 —— 那一刻
  没人再知道工作树和提交态差在哪里。

### 3.58 check 模式读的是工作树里的文件 —— 报告说的却像是仓库里的代码

**现象**：在仓库 A 上跑 `--mode check`，报了一条高危
`discards-error app_test.go:115`（「错误被丢掉，断言却要求它是空的」）。

那条发现是真的（源码确实丢了一个错误）。问题是：**它只在开发者还没提交的
改动里成立**。把 `app_test.go` 改好但**不提交**，再跑一次 check —— 那条高危
**消失了**；报告里没有一句话说明「刚才那条发现不见了，是因为你改了这个文件
但没提交」。

**根因**：check 模式的静态检查读的是**工作树里的文件内容**：

```
files, err := repo.TrackedFiles("HEAD")   // 文件清单取自 HEAD
...
detect.Skipped(root, files)               // 内容却是从工作树读的（os.ReadFile）
```

清单来自 HEAD，内容来自工作树。这两半不在同一个地方，于是报告可能描述一份
**仓库里并不存在**的代码 —— 和 3.57 是同一类病：「报告描述的是一个磁盘上
存在、但提交态里没有的状态」。

**更糟的是**：闸门（`internal/gate/gate.go`）里有一段注释，是「闸门有意不看
被审仓库的工作树」这个设计**唯一的理由**：

```go
// 被审仓库的工作树由工具自己的审计去报（它会把那种情况报成高危）。
```

这句话是**假的**。工具从来没有这个检查器 —— 全仓只有闸门自己在读
`git status --porcelain`，读的是**工具自己**的工作树。审计那边：
反事实和基线两棵树都是用 `git archive` 从提交里建出来的，所以**审计的结论跟
工作树无关**；而 check 模式整个跑在工作树上，所以**check 的结论跟工作树
有关**。这句话把两件事说反了。

**后果**：闸门说「没变化」，但 check 报告的内容可能已经变了（因为工作树
变了）；而报告自己一个字都不提。读报告的人无从知道自己在看的是哪一份代码。

**修复**：

1. 新增 kind `uncommitted-changes`（警告级），在 check 模式里说清楚：
   报告里有哪几条发现指向的文件，工作树里的内容和 HEAD 不一样。
2. **只报那些「真的有发现指向它」的文件**。工作树脏是开发者的常态，一个
   没有发现指向它的脏文件对这份报告毫无影响 —— 报它就是噪音，而噪音是让人
   关掉检查器的原因（3.7、3.52 讲的都是这件事）。
3. 警告级，不是高危。「手上有没提交的改动」是机器的常态，报成高危会让
   `--fail-on high` 在每一次编辑之后都失败，人就会加 `--no-verify`。
4. 把 `gate.go` 里那句假话改成真的：闸门不看工作树（3.23 的理由仍然成立），
   真正把这件事说出来的是**工具的报告**，而且只有 check 模式受影响
   （audit 的两棵树都是从提交里建出来的）。

**负对照**：

1. 把报告里那条 caveat 去掉 → `TestUncommittedCaveatNamesTheDirtyFile` 红。
2. 把「只报有发现指向它的文件」这个条件去掉 → `TestUncommittedCaveatIgnoresUnrelatedDirtyFiles` 红
   （这就是噪音守卫：拿掉它，工具有事没事都会开口）。
3. 把探测器弄瞎（永远返回空列表）→ 4 条测试一起红（2 条 detect 的 +
   2 条 cli 的）。

改回去 → 全绿。

**教训**：

- **报告读的是哪一份代码，这件事本身是报告的一部分**。工具可以读工作树
  （那是 linter 该做的事），但**必须说**。
- **「清单来自 A、内容来自 B」是个能藏住一整类错判的缝**。A 和 B 都是对的，
  合起来却不是同一份东西。
- **注释里的承诺也是承诺**。`gate.go` 那句「审计会报成高危」替一个**不存在
  的检查器**背了书，而它正是某个设计决定唯一的理由 —— 一个查不出来的洞，
  往往是因为有人**读到了注释**就相信了它。

### 3.59 symlink 和 submodule 让检出回退到「会写被审仓」的那条路

**现象**：两种仓库，每一种都被工具静悄悄地写进了：

1. **仓库里有 symlink** —— 检出内容是对的（symlink 还在），但被审仓的
   `.git/worktrees/` 里多了一个 worktree 注册项。`internal/git` 这个包开头
   写着它对被审仓的承诺：「一个字节都不写进去 —— 不写工作树，不写索引，
   不写 ref，连 `.git` 都不写」。
2. **仓库里有 submodule** —— 检出里 submodule 那个位置是**空目录**，构建
   必然失败，于是每个提交都判 `environment`（「环境没搭」）。**这个仓一条
   结论都没有**，而报告看上去是「每个提交都有交代」。

**根因**：`NewWorktree` 先走「零写入」那条路 —— `git archive` 解包，然后拿
解包出来的文件数和树里的文件数对一下。对不上就判定「不是精确副本」，退回
`git worktree add`。而这条回退路**是写被审仓的**（HEAD 上代码自己的注释
写着：「Fallback: git's own worktree. It writes to the audited repository,
so it is a last resort rather than the default.」）。

两件事让「对不上」变成常态：

- `untar` **不数 symlink**。git 眼里 symlink 是树里的一个文件，解包出来
  也是，但计数时跳过了它 → 永远少 1。
- `treeFileCount` **把 gitlink 当成普通文件**。树里 submodule 是一项
  gitlink（钉住的 commit），`git archive` 只带 gitlink 不带内容，解包出来
  是空目录 → 数量对不上。

于是**任何带 symlink 或 submodule 的仓，每次审计都走回退路**。前者写被审
仓；后者写被审仓，而且检出还是坏的。

**为什么值得单独修**：example 那批仓**真的用 submodule** ——
`meta-service` 挂 7 个（admin / relay / shared / http-mock /
http-mock-data / docs / tools），`service` 和 `relay-service` 各 2 个。
（任务说明里写的「用 `replace` 指向 `../shared`」只对 `admin-service` 和
`relay-service` 成立，其余是 submodule。）

**证据**：在 HEAD 的副本上（`git archive HEAD` 解到 `/tmp`）写了一个复现
测试，两个都红：

```
--- FAIL: TestReproSymlinkCheckout
    WROTE TO THE AUDITED REPO: .git/worktrees exists
--- FAIL: TestReproSubmoduleCheckout
    SUBMODULE CONTENT MISSING from the checkout: .../repo/lib/lib.go: no such file or directory
    WROTE TO THE AUDITED REPO: .git/worktrees exists
```

同一份测试换成本次的代码，两个都绿。

**修复**：

1. `untar` 把 symlink 计入文件数（它本来就是树里的一个文件）。
2. `treeFileCount` 把 gitlink 剔出去（它是「另一个仓的指针」，不是这个树的
   文件）。
3. submodule 的内容**从本机对象库里放回检出**：走
   `git archive --git-dir=<submodule 的 git dir> <钉住的 commit>`。**取的是
   钉住的 commit，不是工作树** —— 工作树上可能是别的 commit（开发机上
   一半时间是），那会让反事实实验跑在一个不存在的仓上。
4. 本机上没有那个 commit 的对象 → 明确报 `SubmoduleError`，**点名 submodule
   和钉住的 commit**，并给出该跑什么命令。不猜、不联网。

**负对照**（四条，每条都是「把修复改回去，测试必须变红」）：

| 改坏什么 | 哪条测试变红 |
|---|---|
| symlink 不计入文件数 | `TestWorktreeCheckoutKeepsSymlinksAndWritesNothing` |
| gitlink 又被当成树里的文件 | `TestWorktreeCheckoutIsExactWithSubmodule` |
| 取工作树的 commit 而不是钉住的 commit | `TestWorktreeSubmoduleUsesThePinnedCommit` |
| 根本不落实 submodule | `TestWorktreeMaterializesSubmoduleContent` |

> 第一条是**这一轮补的**：symlink 那处修复原先**一条测试都没有**。
> 拿掉那个 `files++`，整个包的测试**全绿** —— 一个没人看守的修复。
> 按 3.7、3.52 的标准，只报不抓的检查器等于装饰品，补上之后它才算数。

**教训**：

- **「数量对得上」和「内容是对的」是两件事。** 这个工具用文件数当精确性的
  代理，代理一旦偏一个，整个检出就走上一条更贵的路。
- **回退路径的代价是写被审仓**，所以任何让回退变得常见的缺陷，都在偷偷
  消耗「只读」这条保证 —— 而保证不会喊疼，它只是悄悄地不成立了。
- **一个没有人看守的修复，等于没有修复。** 补那条守卫测试花的力气，比
  重写整个 submodule 支持少得多。

**来龙去脉**：这份 checkout 修复是上一轮 cron 核验在运行时崩溃时留下的
未提交改动（`internal/git/submodule.go` 等 5 个文件，10-22 20:35–21:03）。
这一轮判定它是**孤儿**（运行时里没有第二个 agent 拥有这个仓、写作窗口内
没有活跃会话、没有进程占着这些文件、14 小时没人动过），于是**独立复现了
它要修的 bug**（在 HEAD 副本上）、确认它确实修好了、**补上了它缺的那条
守卫**，再收编进仓。收编的理由不是「有人写过了」，是「我验过了」。

### 3.60 编译不过发生在「这次提交改过的文件」上，被说成了「环境缺东西」

**现象**：仓库 A 的提交 `e2d22b7`（`fix(bench): 修 vet 报错（冗余换行）`，
一行改动）被判成：

> `environment`（信息级）：这个提交没法判定：检查出的代码缺东西，跑不起来
> …… 证据：`cmd/alpha-bench/main.go:94:2: fmt.Println arg list ends with
> redundant newline`
> 提示：看证据里的编译错误：缺什么就补什么。本地依赖的，检查一下该目录在不在；
> 生成物的，先构建一次再审

**缺的东西并不缺。** 证据里那行是 **vet 报错**，而这个提交**修的就是它**。
读者照着提示去补「没入库的生成物」，什么也找不到。

**根因**：判决层有一条规则（`verdictFrom` 的编译错误分支）：

> 编译不过，坏在**非测试文件**上 → 依赖动过了，父提交上的代码跟不上了 →
> `environment`

这条规则**没有看那个文件是不是这次提交改过的**。而反事实树是
**父提交 + 测试补丁** —— 那个文件处在**修复被撤掉**的状态。于是：

> 撤掉修复 → 那个文件编译不过 → **这个修复就是让它编译过去的那个修复**

按工具自己的定义（`VerdictCoupled`：「the test could not run without the
fix」），这正是 coupled，而不是 environment。

**证据**：同一个提交，改前改后各跑一次端到端：

```
改前: kind=environment  severity=info
      "这个提交没法判定：检查出的代码缺东西，跑不起来"
改后: kind=coupled      severity=warn
      "无法判定：撤掉修复之后代码就编译不过了"
      "坏掉的那个文件（cmd/alpha-bench/main.go）正是这次修复改过的文件"
```

**修复**：

1. 判决时多带一份信息：这次提交改了哪些文件（`changedPaths(res.Changed)`）。
2. 编译不过发生在**这次提交改过的文件**上 → `coupled`（套件离不开这个
   修复），并把文案换成第三种说法，点名坏掉的是哪个文件。
3. **环境那套 pattern 仍然优先**（`isEnvironmentFailure` 先判）：真·环境问题
   （模块找不到、replace 目录不存在、工具链版本不够）照旧判 environment。
   只有「pattern 都不认识、坏在非测试文件上」这一类才会走到新规则。

**负对照**：把新规则拿掉 → 两条测试变红
（`TestBuildErrorInTheRepairedFileIsCoupling`、
`TestClassifySeparatesCouplingFromEnvironment` 里的新用例），其余用例照旧绿。

> 修这条的时候踩到了一个老坑：**筛选器把守卫筛掉了**。第一次负对照显示
> 「守卫生效次数 = 0」—— 不是守卫没抓住，是**破法本身把包编译坏了，测试
> 压根没跑**。全绿和一条没跑，在输出里长得一模一样。所以脚本里现在先数
> 「跑了几条」，再数「红了几条」。

**顺带修好的**：耦合那种发现的文案以前只有两种（测试补丁打不上 / 测试引用
了修复引入的东西）。新加的第三种说的是「坏掉的是代码本身，而这次修复就是
让代码能编译的那个修复」—— 读者要做的下一步跟前两种**不一样**：
前两种是「这个测试耦合了」，第三种是「这个提交让代码重新编译得过去，
这件事本身有价值，只是覆盖度这个问题在这里没有答案」。

**教训**：

- **「坏在哪个文件」要和「这个提交动了哪个文件」放在一起看。** 这跟 3.58
  是同一族病：一个判断只看了手里的一半事实，另一半就在旁边。
- **「没有答案」有两种，给读者的下一步不一样。** 指错下一步比不给结论更
  糟 —— 读者会照着错的下一步花半天时间，什么也修不到。

### 基线表过期了（3.55 的副作用）

3.55 把「实验没跑起来」从「没有任何测试看守它（高危）」改判成
「`environment`（信息级）」。**仓库 A 的基线因此变了，但基线表没跟着改**：

| 记的地方 | 记的值 | 现在的值 |

| 第 2414 / 2460 / 2539 / 2657 行 | `proven 3 · vacuous 0 · 无测试 4 · 无法判定 6 · 不适用 7` | `proven 3 · vacuous 0 · 无测试 3 · 无法判定 7 · 不适用 7` |

### 3.61 内测脚本漏算了「没有测试看着」那一类 —— 它报的数字比报告本身还小

**现象**：`scripts/try.sh`（内测用的那条命令）在仓库 A 上说：

```
审到提交 : 10
有结论   : 3   （3 条「有测试看守」+ 0 条「没有测试看着」）
判不了   : 5
不适用   : 2
审不成   : 0

── 这次结果算不算数 ──────────────────────────────────
✓ 有 3 条真结论。这次的数字可以用。
```

而同一份报告（`vacuous --mode audit --limit 12 --json`）说的是：

```json
{"proven": 3, "vacuous": 0, "inconclusive": 5, "no_test": 2,
 "not_applicable": 2, "by_kind": {"coupled": 5, "no-test-for-fix": 3},
 "max_severity": "high", "audit_failed": 0}
```

**12 个提交被审过，报告里有 3 条 `no-test-for-fix`（其中 1 条是高危）。**
脚本说「10 个」「没有测试看着 0 条」。

**根因**：脚本自己算了一遍加法，而它漏了一个键。

工具的口径写在 `internal/report/text.go` 的 headline 里：

```go
judged := r.Proven + r.Vacuous + r.NoTest + r.Inconclusive
unjudged := r.NotApplicable + r.AuditFailed
```

`no_test`（这个改动改了行为，但仓里没有任何测试看守它）**是一条结论**，
不是「判不了」。`internal/core/core.go` 里对这个计数的说明写得很直白：

> It is counted apart from Inconclusive because "nobody wrote a test" is an
> answer, not a shrug.

而脚本写的是：

```python
total = proven + vac + incon + na + afail   # ← 没有 no_test
real  = proven + vac                        # ← 也没有 no_test
judged = total - na                         # ← 跟着一起错，还把 audit_failed 算进了「判过」
```

少算一个键不会让脚本崩溃 —— 它只会**报出一个比报告小的数**，然后拿这个数
下结论。这正是这个脚本要防的那种事：「0 条发现」有两种意思，而脚本自己
先把其中一种说成了另一种。

**这个洞为什么之前没被看见**：脚本把 `vacuous`（测试存在但证明不了任何事）
的文案写成了「没有测试看着」，而「没有测试看着」在工具的词汇里是
`no_test`。两个概念共用一句话，少算的那个键就被藏进了另一个键的
影子里 —— 读输出的人看不出少了东西。

**顺带发现的第二个洞**：`△`（有结论，但也有判不了的）那一档**是死代码**。
分支顺序是 `afail → real → judged==0 → incon>=judged → else`，而 `real` 非零时
会在第二个分支就 return，`real` 为零时 `judged == incon`，于是
`incon >= judged` 恒真 —— `else` 永远到不了。也就是说：

> 一次运行里既有 5 条结论、又有 5 条判不了的提交时，脚本只会说
> 「✓ 这 3 条真结论，这次的数字可以用」，**那 5 条判不了的一个字都不提**。

README 里写了 `△` 这一档，但它从来没有出现过。

**修复**：

1. 脚本按工具自己的口径算：`judged = proven + vacuous + no_test + inconclusive`、
   `unjudged = not_applicable + audit_failed`，`real`（有结论）= proven + vacuous
   + no_test。
2. 三个概念各说各的：`proven` 是「有测试看守」，`vacuous` 是「测试形同虚设」，
   `no_test` 才是「没有测试看着」。
3. 分支按「有多少结论」排，不按「有没有结论」排：`△` 这一档因此第一次真正
   走得进去。判不了的提交不该被一个 ✓ 盖住。
4. 报告里有洞（`audit_failed > 0`）而一个结论都没有时，多说一句
   「✗ 一个提交都没审成」，别让它掉进「这个窗口里没有值得审的提交」。

**修复后同一个仓的输出**：

```
审到提交 : 12
有结论   : 5   （3 条「有测试看守」+ 0 条「测试形同虚设」+ 2 条「没有测试看着」）
判不了   : 5
不适用   : 2
审不成   : 0

△ 有 5 条结论，5 条判不了。判不了的那些不算「没问题」。

  [high] no-test-for-fix  这个改动改了行为，但仓里没有任何测试看守它
```

**负对照**：新增 `internal/scripts/try_test.go`。它**跑真的脚本**，喂给它的
JSON 由工具自己的 `report.RenderJSON` 生成 —— 不是手写一份长得像的假数据。
这样工具改字段名时脚本会跟着失效，而不是各算各的。

两条破法都要让测试变红：

1. 把 `real = proven + vac + notest` 改回 `real = proven + vac`（= 原来的 bug）
   → `TestTryScriptTallyMatchesTheReport` 变红。输出里能直接看到症状：
   三个分项写着 `2 + 0 + 1`，加起来却是 `2`。
2. 把分支顺序换回旧的（`△` 变成死代码）→
   `TestTryScriptVerdictPerSummary/conclusions_mixed_with_undecidable_commits`
   和 `.../the_audit_could_not_finish` 变红。

改回去后照旧全绿。

**教训**：

- **同一个数只能有一个算法。** 脚本自己算一遍加法，就得跟工具算的一模一样；
  两处各写一遍，差一个键的时候没人看得出来。
- **「共用的文案」会把缺失的键藏起来。** `vacuous` 和 `no_test` 都叫「没有
  测试看着」，少算的那个键就有了替身。下游要改名字的时候，顺手把两个
  概念分开，比补一个键更值钱。
- **文档里写了、代码里走不到的那一档，也要算 bug。** README 承诺的 `△` 从来
  没出现过 —— 承诺和实现要对得上。

### 3.62 闸门对被审仓库只有一只眼睛 —— HEAD 没变，但工作树变了

**现象**：`scripts/gate.sh check` 报 `NO CHANGE`、退出码 0。

同一时刻，6 个被审仓里有两个的工作树是脏的：

```
beta     M examples/alpha-notes/graph.json     （改了没提交）
epsilon   M src/styles/base.css                 （改了没提交）
```

闸门一个都没报 —— 因为对被审仓，它只比 HEAD。

**为什么这要命**：check 模式读的是**工作树里的文件**（3.58 记过这件事：清单取自
HEAD，内容从工作树读）。于是同一个 HEAD 下，工作树改了没提交，跑出来的结果
是不一样的。实测（拿 beta 的副本做，HEAD 一点不动）：

| 工作树 | 跑出来的发现 |
|---|---|
| 干净 | **1** 条（`guard-not-installed`） |
| 给一个测试文件加一行 `t.Skip` | **3** 条（多出 `skipped-test` 警告 + `uncommitted-changes` 提示） |

闸门说「没变化」→ 这一轮不重跑 → 手上的报告描述的是**上一次核验时**的工作树，
而现在的工作树已经不是那一个了。

症状和「一切正常」完全一样：`NO CHANGE`、退出码 0、CI 绿。

**根因**：3.23 修的是工具**自己**的工作树看不见（假阴性），并且明确把被审仓的
工作树排除在外，理由是：

> 某个被审仓库的工作树里一直有用户正在开发的未提交源码，把它算进去，闸门就每一轮
> 都喊「有变化」—— 正是 3.18 那个自毁的毛病。**这条是有意的取舍，不是漏掉。**

这个理由本身没错，但那个排除**继承了一个前提**：判据是「现在是脏的就算数」。

工具自己的仓用这个口径是对的（它归我们管，工作树脏了就是「这次核验跑的不是
HEAD 里那份代码」）。被审仓用**同一个**口径就是 3.18 复发 —— 3.23 当时是在
两个口径之间二选一，而不是把口径拆开。3.58 把那句假话（「审计会报成高危」）
纠正了，但没有碰这个取舍本身。

**修复**：被审仓改用**第三个口径** —— 「和上次记录时不一样」才算数。

- 基线里多记一份每个被审仓工作树的指纹（`WorkingFingerprint`）：把「与 HEAD
  不同的那些**被跟踪**文件」的路径和内容哈希起来；工作树干净 = 空指纹。
- `Check()` 多比这一项：对不上就报 `target-dirty`（退出码 1，和「代码变了」
  同一处理）。
- 记基线时把当前指纹一并记下（`Target.Working`）。**所以被审仓长期脏着不会让
  闸门每轮都响** —— 只有它真的动了才响。

三条边界：

1. **只算被跟踪的文件**。未跟踪的（`.mavis/` 这种草稿目录、编辑器备份）不在
   check 的分析范围里 —— 它们在磁盘上，却不是这个仓的一部分。算进来，闸门就
   天天响。
2. **比的是「和上次不一样」，不是「现在是脏的」**。这是全部的关键：被审仓不是
   我们一个人的，「脏」是常态，「变了」才是要重跑的理由。
3. **文档照样算**。工具自己的仓排除文档，是因为我们自己每轮都提交文档；被审仓
   的文档不在那个豁免范围里。

**修完之后的实测**（基线是旧的、没有工作树指纹，所以两个脏仓都被认出来）：

```
CHANGED:
  - [dirty]        工具代码有未提交的改动（3 个文件）：…
  - [target-dirty] 被审仓库 …/beta 的工作树变了（未提交的内容和上次记录时不一样）
  - [target-dirty] 被审仓库 …/epsilon 的工作树变了（未提交的内容和上次记录时不一样）
```

alpha 和 zeta **没有**被报 —— 它们脏的地方只有未跟踪的 `.mavis/`，
按边界 ① 不算数。

**负对照**（三条都要让测试变红）：

| 拆掉的修复 | 变红的用例 | 保持绿 |
|---|---|---|
| `Check()` 里比工作树指纹那段 | `TestCheckReportsTargetWorkingTreeChange`、`TestCheckReportsTargetWorkingTreeContentChange` | `TestCheckIsQuietWhenTargetWorkingTreeIsUnchanged`、`TestCheckIsQuietWhenTargetHasOnlyUntrackedScratch` |
| 指纹里去掉内容哈希（只留路径名） | `TestCheckReportsTargetWorkingTreeContentChange` | `TestCheckReportsTargetWorkingTreeChange` |
| 把未跟踪的文件也算进指纹 | `TestCheckIsQuietWhenTargetHasOnlyUntrackedScratch` | 其余三条 |

第三条最要命：把未跟踪文件算进来，闸门就会天天喊「有变化」—— 3.18 那个自毁的
毛病，在另一个位置复发。所以「被审仓工作树」这条判据必须同时有**该报的时候报**
和**不该报的时候安静**两组测试。

**教训**：

- **「排除某样东西」的理由，可能只对那时的那个口径成立。** 3.23 的排除没错，
  但它把「脏就算数」这个口径一起继承了。口径一拆开（脏 / 和上次一样 / 变了），
  两难就不存在了 —— 新口径既没有漏报，也没有 3.18 那种天天响。
- **一个仓的 HEAD 没变，不等于这个仓没变。** check 读的是工作树；只盯 HEAD
  的闸门对 check 模式永远只有半只眼睛。
- **闸门对自己的每一只眼睛，都要有两组测试**：该报的时候报、不该报的时候安静。
  只补第一组，闸门就成了一个「逢事必报」的噪音源。
